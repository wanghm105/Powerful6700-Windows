## 2 0x10000004：确凿事实（可以直接拿去对日志）

✅ **它长什么样**：`Jiritsu 状态 0x10000004`，原始字节 `04 00 00 10`（小端）。在 GUI 里显示为「相机拒绝了配置写入（SET_FILE2）（file_id=0）：状态 0x10000004」。

✅ **出错的层**：category `0x1001`（Jiritsu 文件服务）下的文件命令。同一会话里：
- `REMOVE(18)` 三条临时路径 → 全 0x10000004；
- `READ(17)` 读 `/setting/BACKUP.BIN` → 0x10000004（连普通文件都读不出）；
- `SELECT(15)` 三条路径 → **都不报错**（这就是「定位没被拒」）；
- `WRITE`（0x4010 配置写入的 `file_id=0`）→ 0x10000004。

✅ **它跨什么**：跨电脑（机友 B / 机友 A / 机友 C 的机器）、跨 Windows 版本（26300 / 26340 / 28000 都是 Insider，健康机是 26200）、跨 probe 版本（probe1 / probe2 / probe3 / probe4r 都复现）。**唯独 0.3.8 在健康机上一直是好的**。

✅ **probe4r 试过并且都没用的 12 种办法**：清残留重写、等 0.5/1.5/3 秒、只写 1 字节、读一个普通文件、再等 8 秒、把三条路径逐条 select 后重写、**把整个服务会话关掉重新认证一次**（这一次它成功了，但写入照样被拒）。

✅ **那条「重开会话」有副作用**：probe4r 这一次把相机从 `0x0E76`（MSC）推到了 `0x096F`（HidUsb，文档里写着「救不回」），收尾 `[Errno 32] Pipe error`。所以 probe5 里这段代码被整块删掉，注释写着「别再放回来」。

✅ **不是这些**：不是临时文件残留（连读普通文件都拒）、不是时间窗（等 3/8 秒无效）、不是驱动没装（`device_access=true`、`winusb` 在、九项自检过）、不是诊断包坏了（`plan={}`、问题 0 处，说明根本没走到结构守卫那一步）。

## 3 猜想：为什么文件服务不可用

### H1 nflasha6 分区没挂上（🔶 最可能）
机制：`/tmp/jiritsu` 在独立 flash 分区 nflasha6；FX30 6.00 上有人实测「删掉 `/tmp/jiritsu/libJit.so` 会让 Jiritsu **卸载整个 nflasha6**，此后所有文件命令一律被拒，补救只有发 `0x4002(MOUNT)`」。分区卸载后，`/tmp/jiritsu` 的读会直接回 **130**（= 分区已卸载），而不是「文件不存在」。

为什么它最像：失败现场的三个特征（select 成功、remove/read/write 全拒、跨电脑跨版本一致）与「分区不在挂载表里」完全同型。

### H1a 我们自己把机友的分区卸了（🔶 高置信，且不太好意思）
- 0.3.8 的清理名单**没有** `libJit.so`；probe1–probe4r 的名单**加了**它，删完**从不重挂**。
- 也就是说：机友第一次跑 probe1/2/3 时，如果相机里刚好留着 libJit.so，那一次就把分区卸了；此后只要相机**没有真正断电冷启动**，后面每一版都会 0x10000004。
- 这条能解释「越试越坏」「重装软件没用」「换电脑也一样」。
- probe5 的修法：删掉 libJit.so 之后**当场** `0x4002` 重挂（`patches.py:294-304`）。
- **需要问机友一句话**：第一次遇到 0x10000004 之前，跑的是哪个版本？如果是 0.3.8 且从没跑过 probe1–3，那 H1a 不成立，退到 H2/H3。

### H2 文件服务需要前置命令，我们从来没发过（🔶）
健康机上 0.3.8 能跑通，说明「先 0x4010 再文件命令」这套顺序在健康机上够用；但如果某台相机在上一次会话里把分区卸了，就没有任何前置能补救——除非发 MOUNT。这条与 H1 是同一枚硬币的两面。

### H3 整个 category 0x1001 服务没起来（❓）
如果 Jiritsu 这个相机侧进程压根没就绪（相机 app 半启动、上一次会话崩了），错误可能也长成 0x10000004。
**probe5 的第一刀就是为此设计的**：`0x400D(GET_VERSION)` 是会话里第一条命令，如果它**也**回 0x10000004，那问题不在文件层，而在整个服务层（相机侧进程/协议版本）；如果它回了 4 字节版本（例如 `02 00 00 10` = 2.00），就说明服务活着，问题只在文件/挂载层。

### H4 有别的句柄/进程占着分区（💡）
Windows 侧 WPD/资源管理器扫描、我们自己上一个会话没释放的句柄、相机侧残留的 file id。判据：同一台相机在同一 PID 下的第二次运行会不会变好；拔掉所有其它 USB 设备会不会变好。

### H5 host 侧时序（❓）
失败机都是 Insider（26300/26340/28000），健康机 26200。相机返回值理论上不该受 host OS 影响，除非 USB 栈时序让第一个 Jiritsu 包的「命令/正文」错位（那样返回值会变成无法识别的垃圾，而不是稳定的 0x10000004，所以我不太信这条）。判据：同一台失败机换 USB 2.0 口、换线、换另一台电脑（机友 C 已经跨电脑复现，所以这条权重低）。

### H6 相机被更早的写入弄脏了（❓）
issue 用户可能先用 0.3.7 解锁过功能（写过 /setting 或 CP），留下不一致状态。判据：官方固件重刷 2.00 / 相机初始化之后是否恢复。**注意这条要用户自己承担风险**，我们不该主动建议刷机。

## 5 最便宜的三个实验（比改代码快）

1. **同一台失败机，跑 0.3.8 对照**（10 分钟）：如果 0.3.8 也 0x10000004，说明相机侧状态坏了，不是 probe 的锅；如果 0.3.8 好了，就是 probe 引入的（H1a）。
2. **相机彻底断电冷启动**：拔 USB → 关机 → **取电池等 1 分钟** → 装回开机 → 再跑。这条能把「分区没重挂」与「相机侧真坏」分开。
3. **只读不写的最小路径**：用 probe5 跑一次、把日志整段发我（日志里 0x400D/0x4002 两行就够定性）。

## 6 相机侧机制（已知，✅）

- Senser 帧头 12 B：`struct.pack("<IHHBBBB", len(body), 0x40, seq, 0,0,0,0)`；PF `0x10` = ProductInfo，`0x40` = 命令通道。类别与命令：`struct.pack("<HH", category, command)`。
- 文件服务：category `0x1001`；命令 `SELECT=15 / WRITE=16 / READ=17 / REMOVE=18`；另有 `0x400D GET_VERSION`、`0x4002 MOUNT`（空正文）、FX30 上还有 `0x4009 / 0x4012` 两个删除候选、共 `0x4001–0x4012` 18 条。
- 文件槽位表（`libJiritsu.so` 里 `get_jiritsu_area_filename()` `0x1236C`）：0=`tmmc.jit`、1=`DIAC.csv`、2=`libJit.so`、3=`jit.log`、4=`history.txt`；>4 走 `0x470AD8` 的 34 项表。
- 挂载点：`nflasha2=/setting、3=/system、8=/cp、10=/tmp、11=/log、12=/cert、15=/usr（ext2 ro 可写）、18=/lens`；**nflasha6 = /tmp/jiritsu**，约 25 MB。
- 写通道：`0x4010` 配置（`SET_FILE2`，`file_id=0` 是我们自己的载荷文件）、`0x4007` 载荷（`SET_FILE`）、`0x4008` 执行（`EXECUTE`）。我们**只发前两个**，0x4008 从未发过。
- 白名单（native 侧）：可写 `/usr/、/cp/、/setting/`；可读再加 `/system`；拒绝 `/../` 与 `/dev/`。
- USB 读超时 `timeout=10000`（`third_party/a6700_unlock/usb/legacy.py:545 class SenserChannel`）⇒ 任何一条命令最坏多等 10 秒，不会永久挂住。
- 状态码表：`STATUS_TEXT 0..14`（12 = 范围超出文件长度、6 = 路径不在白名单、9 = 回读校验失败、10 = 数据文件缺失或长度不符、14 = 截断失败）。

## 7 我们的写入路径（✅，probe5 没有放大风险）

- 只走 `0x4010`（写 `/tmp/jiritsu/tmmc.jit` 这份配置）；不发 `0x4008`、不碰 `/usr`、`/cp`、`/setting`。
- 大文件写入（FL2/FL3 那次用过）：先 `ftruncate` 到目标长度，再按 `WRITE_BLOCK=0x20000` 分块 `pwrite + fsync + 独立只读句柄回读`；`native/flash_write.c` 的 `open_writable()` 是「遇 EROFS 才 remount rw，写完还原 ro」。
- 写事务返回码：1 preimage 变化 / 2 非法请求 / 3 打不开分区 / 4 读短 / 5 写失败 / 6 fsync 失败 / 7 回读不一致 / 8 回滚不完整；没有强制写入开关。
- 结果分类：completed / no-op / blocked / rolled-back / uncertain / verification-failed / recovery-required。

## 8 已证伪（❌ 别再试，会浪费时间或把相机搞坏）

**关于外观槽与 CP**
- ❌ 「用 chroma 记录 23（参数 `+55=23`）给 5VV2 单独上色」：涂记录 23 后 5VV2 与 VV2 三次配对逐像素相同（Y 差 0.2–0.4%）。原因是 A 层 override 只在 `w1 == 0`（基底 = ST）时触发，`5VV2` 的基底是 `VV2`（`w1=4`），指向 mode 19 的代码根本没执行。
- ❌ 「六个自定义槽各装一个 look」：同样卡在 `w1 == 0` 这个前提上，除非改 A 层的比较逻辑（未验证，风险高）。
- ❌ 「CP 参数 `+55/+56` 决定槽位」：改 6/4 没有任何可见变化，已还原。
- ❌ 「写 CP 参数 `+57..+60`」：切到 ST 闪屏重启，回退后才恢复。
- ❌ 「把 chroma 记录 16 当第五个自定义槽」：涂了没人读；记录 8 就是 FL。
- ❌ 「参数表尾部 10 字节 `[16,8,14,10,12,9,15,11,13,19]` 是记录表」：不是。
- ❌ 「chroma 层的蓝端旋钮」：pair1×0.40 把青蓝 1.07→1.37（方向反），pair7/10/11×0.40 只到 1.08。真正的蓝端旋钮在矩阵单元 `0x02A4000D` 的 block 4（整块填 20000 → PT 蓝 0–30° 档 6.20 倍），块内二分还没做。
- ❌ 「菜单里出现 FL2/FL3 字样」可以靠改 UXC/改 160 B 记录表实现：列表名是**运行时拼的**「序号 + 基底名」（`1ST/2FL/3IN/4SH/5VV2/6BW`），改字符串无效。160 B 记录表（`0x04B597AC`，16 条）写了 16 B 后冷启动无变化，已还原。

- ❌ 「上游 payload-integrity 能校验我们的载荷」：上游 manifest 的 `source_sha256` 与 `transaction.c` 不符，已降级为溯源。

**关于文件服务**

## 11 其它悬案

- **CC 蓝端压不下去**：色度层拟合到 0.164（离线 RMS）就到底了；黄绿 0.49 vs 0.69、青蓝 0.95 vs 0.76、330–360° 蓝 0.97 vs 0.53。摘掉蓝端四档重算 RMS 只有 0.137。⇒ 蓝端必须走矩阵层。
- **四配方落点**：CC→记录 6 / NC→记录 4 / PF→记录 1 / NF→记录 14（写回内置外观），这是「独立槽」证伪后的退路。仓库里 `docs/looks-profile.json` 目前仍是 CC pair2×0.519（rms 0.183），比文档里记的 0.164 版本旧——**更好的配方没烘进代码**。
- **A7C2 可搬的四块**：机身绑定摘要、载荷形态（installer.c）、factory-regions 身份门、色表尺寸表（gamma 576 / 矩阵 576 / 色度 64 / 网格 1215，768 只写前 576）。
- **矩阵 block 4 的 int16 标定**：整块填 20000 能让 PT 蓝 0–30° 档翻 6.20 倍，但块内哪个 int16 管哪一档没做二分——需要相机能开机才做。
