# cpapp 静态层调查（A6700 2.00）

> 目的：找到 A6700 机身里「外观 = 颜色 + 影调」的静态载体，照 A7C2 的写法落地 CC/CN。
> 全部离线完成，未改动相机。

## 1. 已确认的骨架（与 A7C2 同构）

cpapp-b.bin（17,892,024 B = `0x11102B8`，ARM32 Thumb 裸镜像，不是 ELF）的头部区 `0x20140` 存**初始化数据长度**：

| 项目 | A6700 2.00 | A7C2 2.01 |
|---|---|---|
| 长度字段位置 | `0x20140` | `0x20140` |
| 长度值（原厂） | `0x001412B8` | `0x00141B80` |
| 初始化数据块起 | `0xFBF000` | `0xFBF000` |
| 块结束 = 起 + 长度 | `0x11002B8` | `0x1100B80` |
| 文件长度 | `0x11102B8` | （A7C2 打完补丁后同量级） |
| 块后剩余空间 | `0x10000`（65,536 B） | `0xF20` 被 A7C2 追加用掉 |

**A7C2 的落地机制（数值已验证）**：`0x142AA0 − 0x141B80 = 0xF20 = 3872`，正好等于它在 `0x1100B80`（= 原块结束处）追加的 3872 字节；也就是说 A7C2 的做法是「在初始化数据块末尾追加数据 + 把长度字段改大」，不是覆盖既有内容。

对 A6700 的直接推论：块结束在 `0x11002B8`，文件还有 `0x10000` 字节余量，**追加通道是开着的**；要落地我们自己的曲线记录，改 `0x20140` 的长度 + 在 `0x11002B8` 之后追加即可，不破坏任何既有数据。

## 2. 静态候选：9 条 1024 B 恒等曲线

`0xFE0B50` 起，步长 `0x400`，共 **9 条完全相同的 1024 B 记录**，最后一条结束于 `0xFE2F50`，之后全是 0：

- 每条 = 512 个 u16；形状是分段线性的**恒等映射**：0 → 61440 每步 4096（16 段），61440 → 65280 每步 256（16 段），65280 → 65535 每步 1，之后填 65535。
- 位于初始化数据块内（`0xFE0B50 − 0xFBF000 = 0x21B50`）。
- 9 条完全相同 ⇒ 出厂模板，运行时按外观/模式填入真实曲线。

## 3. 负结果（别再重复这几条路）

- **没有 ADR 引用**：`tools/t32ref.py` 扫 `[0xFE0B50, 0x1103000)` 得 1591 命中，全部是斜坡数据自身造成的假命中（第 10 个值恰好 `0xA000`）。
- **没有 32 位字面量引用**：全镜像搜 `u32 & 0xFFFFF0 == 0xFE0B50` 只有 1 处（`0x1029E50 = 0x0EFE0B55`，属噪声）。
- **没有 9 项指针表**：搜「9 个连续 u32、步长 0x400」只命中 `0xBD1E38` 一带，隐含基址为负 ⇒ 伪命中。
- **没有块相对偏移常量**：`0x21B50` / `0x1412B8` 不在任何 `MOVW/MOVT` 常量里（全镜像只有 665 对，说明编译产物主要用 ADR / 基址寄存器，不走绝对地址）。
- 长度字段 `0x1412B8` 在镜像里只出现 1 次（就是它自己） ⇒ **消费者在 cpapp 之外**（加载器 `mini_ldr.bin` / `loader_spi.bin` 或 ROM），cpapp 自身代码不读这个字段。

结论：这 9 条记录从 cpapp 代码侧找不到引用点，它们要么由加载器整块搬进 RAM 后由别处按固定偏移取用，要么当前根本不参与静态照片渲染。**只能靠真机实验判定**。

## 4. 其它扫描结果（未定性 / 判为噪声）

- appFw-2.00.so 里 129 点 u32 单调曲线只有 3 条（`0x37571AC` / `0x4C495B4` / `0x4C50654`），长度和量级都不像外观曲线。
- cpapp 里 129 点 u16 严格单调曲线 12 条：其中 9 条就是上面的恒等斜坡；另外 `0xD92810`、`0xD92A10`、`0xE465C4` 落在长斜坡数据区（相邻表首尾相接），不是独立记录。

## 5. 下一步：一次可回滚的真机判定实验

**问题**：这 9 条恒等曲线是否影响静态照片的影调？

**做法**（全部可回滚，写入前先读回整份 cpapp 做备份）：

1. 读回真机 `/cp/cpapp-b.bin`（17,892,024 B），存 `../firmware/cp/cpapp-live.bin` 并核对 sha256。
2. 把 9 条记录全部改写成一条**明显但不破坏性**的曲线（例如 gamma 1/2.2 提亮曲线，或强 S 曲线），长度字段不动（数据仍在块内，不需要追加）。
3. 用 `flash.write_windows` 按 1024 B 窗口写入 9 处，逐块回读校验。
4. 关机重启，拍 ST / PT 各一张同机位照片，与原状态对比。
5. 无论结果如何，用备份整份写回还原。

**判读**：

- 影调变化 ⇒ 这一层就是「外观影调」的入口，接着做「哪一条对应哪个外观」的二分，再把 CC/CN 的曲线写进去。
- 无变化 ⇒ 该块不参与静态照片，转去 appFw 侧的 look 表（`0x4926E40`）与 CP 颜色单元，放弃 cpapp 曲线层。
