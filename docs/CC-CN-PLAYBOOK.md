# 外观（Creative Look）改造手册 —— 名字与颜色

> **缩写说明**：早期研究阶段的内部代号写作 `CN` = Classic Negative；软件界面、README 与相机菜单统一写 `NC`。文件名（`docs/CC-CN*.md`、`tools/apply_cc_cn.py`）保留历史名，不改。

> 本文件是操作手册：记录**怎么改**名字、**怎么改**颜色、**怎么还原**。
> 当前状态（2026-10-24）：**已全部还原到出厂** —— 色度单元 `0x02A40001` = 出厂副本
> `sha256 72d3da86…`，菜单名回到 ST/PT/NT/VV/VV2/FL/IN/SH/BW/SE + 6 个自定义位。

## 0. 一句话结论

- **名字**：在 `/usr/share/app/string_simplifiedchinese_f.uxc`（及同目录的其它语言文件）里，
  按 `rid` 找到记录，就地改 UTF-8 文本。**记录容量由下一条记录的偏移决定**，不是由 NUL 位置。
- **颜色**：在相机内存 CP 单元 `0x02A40001` 里，位置 `0x1250 + bank × 64`，每条 64 字节 =
  **32 个 int16**（前 24 个有效 = 三组 × 8，最后 8 个恒为 0）。
- **持久化**：CP 单元是 RAM，**不保证跨关机保持**。想持久必须写 `/setting/BACKUP.BIN`
  （关机时相机自己会把 CP 单元写进去，偏移见 `docs/PERSIST-STORE.md`）。

## 1. 名字：UXC 记录怎么改

文件：`/usr/share/app/string_simplifiedchinese_f.uxc`（145,612 B，v7 格式）

- 头：`0x00` magic `uxc\x07\0\0\0\0`，`0x10` u16 count（本文件 4785），`0x14` u16 group(227)。
- 记录区起点 `base = (16 + count * 2 + 3) & ~3`（本文件 0x2574）。
- 每条记录：`u32 rid | (0x1E << 24)` + UTF-8 文本 + `\0` + 4 字节对齐补齐。
- **能力上限（易踩）**：容量 = **下一条记录的起始偏移 − 本记录偏移 − 4**。
  用 `NUL 位置` 算会低估（我们就是这样把 `NC → VV2` 判成「容量不足」）。
- 改名只能**变短或等长**；变长必须整体后移、改 count 并重算索引（未验证，不建议）。

### 外观短名所在的记录（`string_simplifiedchinese_f.uxc`）

| 外观 | rid | 偏移（第一组） | 偏移（第二组） |
|---|---|---|---|
| ST | 0x021c658e | 0x00C42C | 0x01E52C |
| PT | 0x021c6654 | 0x00DA94 | 0x01DE98 |
| NT | 0x021c6434 | 0x00A20C | 0x01E680 |
| VV | 0x021c687b | 0x0117DC | 0x01DDD4 |
| VV2 | 0x021c689a | 0x0119F0 | 0x01DA94 |
| FL | 0x021c6cc9 | 0x019098 | 0x01E3B8 |
| IN | 0x021c6857 | 0x01127C | 0x01EE90 |
| SH | 0x021c6961 | 0x012CFC | 0x01D710 |
| BW | 0x021c65f8 | 0x00CF98 | 0x01DBD8 |
| SE | 0x021c658a | 0x00C3C4 | 0x01E828 |

两组都要改：第一组用于部分界面，第二组用于创意外观列表（只改一组会出现「有的地方变了有的没变」）。
自定义位 `自定义1/2/3` 的 rid 是 0x021c7182 / 0x021c717f / 0x021c7180，文本在 0x020DE4 / 0x020DB8 / 0x020DC8。

### 写入流程（实测可用）

1. 认证进服务模式，`flash.read_range` 分块读完 145,612 B（chunk ≤ 0x80000）。
2. `uxc.decode(raw)`，按文本或 rid 找记录，算出容量（下一条偏移法），就地写文本 + `\0` + 补 0。
3. `flash.write_block` **按 32,768 B 分块**写回（`flash.BLOCK = 0x8000`，单次不能超过）。
4. 再 `read_range` 整体回读比对，不一致就报错。
5. 会话结束发 `STOP_SENSER`，相机掉回 0x096F，需手动切 MSC。

工具：`tools/look_name.py`（单条改，含 ChannelBackend）、`tools/apply_cc_cn.py`（CC/NC 一键）、
`tools/restore_original.py`（一键还原）。

## 2. 颜色：CP 单元 `0x02A40001` 的布局

- 单元大小 8,192 B，实测非零约 2,815 B。
- 参数表 `0x1200` 起，1 字节/参数；`40..49` = `[16,8,14,10,12,9,15,11,13,19]`（疑为十个基础外观的 bank 索引）。
- **色度记录**：`0x1250 + bank × 64`，共可容 54 槽（8,192 − 0x1250 = 4,768 = 74.5 槽）。
- 记录 = 32 个 int16：
  - 前 24 个 = 三组 × 8，对应 RAW 标签 0x7842 / 0x7844 / 0x7845（三光源端点）。
  - **`v6` 在所有基础外观恒为 563**；`v4`/`v5`/`v7` 随外观变化。整条全 0 = 完全去色（黑白）。
  - 后 8 个恒为 0。
- 机内 v ↔ RAW r 换算（R5 社区文档，已实测往返）：
  `r = [v3, v0, v1, v2, 2*v7, 2*v4, 2*v5, 2*v6]`，`v = [r1, r2, r3, r0, r5/2, r6/2, r7/2, r4/2]`。
- **注意**：`M = [[a+b+1024,-a,-b],…]` 那套 1024 基底公式**只属于 block13（单元 0x02A4000D 的矩阵）**，
  **不适用于 0x02A40001 的这 8 个值**。曾按该公式推导并写入，结果是「全 0 = 黑白、整体偏一个通道」，据此已推翻。

### 外观 → bank 账本（全部经目视二分确认）

| 外观 | bank | 出厂记录（前 8 int16） |
|---|---|---|
| ST（含 1ST） | 0 | -198, -269, -221, -51, 415, 545, 563, 521 |
| VV | 1, 2 | （bank1/2 各一份） |
| NT | 4 | -207, -269, -279, -51, 433, 461, 563, 385 |
| VV2 | 5 | （bank5） |
| PT | 6 | -211, -259, -204, -51, 412, 505, 563, 493 |
| FL（含 2FL） | 8 | -184, -263, -384, -269, 356, 260, 563, 253 |
| SE | 9 | -395, -81, -306, -269, 306, 352, 558, 345 |
| IN / SH | 10–19 | |

- **BW 没有独立色度记录**（黑白由外观类型本身决定）。
- 自定义位（菜单最后 6 个）**没有独立 bank**：它们是内建外观的别名 —— 把 bank 0 涂粉，
  ST 与 1ST **同时**变粉；把 bank 22–27、30、31、40–53 涂粉，6 个自定义位毫无变化。
- 因此「新增两个独立外观」在色度层不可行，只能**占用两个内建外观**。

### 写入颜色（实测可用）

1. **必须以实时单元为基线**：先 `CpReader.read_unit(0x02A40001)` 读出来，只改目标槽。
   用历史快照当基线会把别的外观一起写坏（曾把 ST/VV 写成黑白）。
2. 改槽：`off = 0x1250 + bank*64`，写 64 字节。
3. `CpWriter.write_unit` 整块写回，内部 fsync + 回读校验。
4. **ISP 只在「外观切换 / 模式切换 / 开机初始化」时重读 bank** —— 写完画面没变化时，
   先切到别的外观再切回来。

### 已知的失败模式

| 症状 | 原因 |
|---|---|
| 整个外观变黑白 | 该 bank 记录被写成全 0（全 0 = 完全去色） |
| 蓝色溢出 | 只缩 `v4/v5/v7` 不缩 `v6` 时，蓝通道相对被抬高 |
| 关机重开颜色消失 | CP 是 RAM；`BACKUP.BIN` 的写入发生在关机流程，我们写 RAM 后不一定被固化 |
| 只有部分界面名字变了 | UXC 的两组记录只改了一组 |

## 5. 为什么 A7C2 能在菜单最后「复制很多个 ST」

A7C2 的固件里本来就有**比菜单显示的更多外观槽位**，社区补丁只是把它们打开：

| 层 | A7C2 | A6700 2.00 |
|---|---|---|
| 外观槽表 | 有 `look16/look17`，菜单产品标志位关着 | 只有 `look0..look15`（10 基础 + 6 自定义），**没有 16/17** |
| look→CP 模式转换表 | 10 项，补丁把它扩到 12 项（索引 10→0x13、11→0x14） | 同样 10 项，但**其后的表没有备用空间也未验证** |
| CP 颜色 bank | FL2/FL3 用**专属 bank 23/25**（参数 55/56），bank 22/24 是 donor | 实测 bank 22–31、40–53 **不挂任何外观**，自定义位共享内建 bank |
| CP 影调 | 补丁往 cpapp 追加 3,872 字节 gamma 曲线记录并改长度字段 | cpapp 里 9 条恒等斜坡**对外观无影响**（已用照片量化排除） |

也就是说 A7C2 的「复制 ST 再加颜色」= 新槽位（固件自带）+ 新 CP bank（固件自带）+ 打开开关的补丁；
A6700 这三样都缺，尤其是**自定义槽位没有独立的颜色 bank**，这是硬约束。

## 6. 为什么「还原了但看起来没还原」——BACKUP.BIN 才是真正的持久源

CP 单元是 RAM，`/setting/BACKUP.BIN` 是它的持久副本，**相机在关机时把 RAM 写进 BACKUP，开机时再读回 RAM**。
只还原 RAM 不还原 BACKUP，就会出现「当场看是对的、关机重开又变回去」。

还原的完整步骤（实测）：

1. 逐个单元与出厂副本比对：`tools/cp_verify_factory.py`
   （出厂副本在 `/setting/def/BACKUP.BIN`，偏移见 `docs/PERSIST-STORE.md`）
2. 把不一致的单元整块写回 RAM：`tools/restore_units.py --confirm yes-write`
3. **让用户正常关机、等满 1 分钟再开机** —— 相机会把当前 RAM（已经是出厂值）写进 BACKUP.BIN，
   从此 BACKUP 也是出厂值。这一步不做，下次开机就会把旧的实验数据读回来。

**2026-10-25 补测（关键细节）**：关机后**立刻**再开机，改动不会落盘——内存与 BACKUP 都退回旧值，
看起来像「写 RAM 没用」。同一次写入之后，正常关机并等 7 分钟再开机，内存与 BACKUP 两处都变成
出厂值（整单元 0 字节差异）。差别只在关机后等待时间，所以「关机等一会儿」是**必要条件**，
不是操作习惯问题。写盘在关机流程里异步进行，等满 1 分钟足够；断电或立刻开机都会丢。

已核对的出厂状态（2026-10-24）：`0x02A40001 = 72d3da86…`、`0x02A4000D = 59aed2ed…`、
`0x02A40000 = fa1af894…`、`0x02A4000E = 66dcee7a…` 全部与 def 副本一致；
写入时 BACKUP.BIN 里的 0x1B2140 / 0x1B6870 仍是旧实验数据（差 75 / 453 字节），必须靠一次关机流程刷新。
