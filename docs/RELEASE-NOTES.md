# Powerful6700 · Windows 0.3.5-win.1

Sony A6700 工具 [Powerful6700](https://github.com/xyzhangxin/sony-a6700-powerful)（上游 0.2.0，GPL-3.0）的 Windows 端实现。

## 0.3.5：颜色和名字一次写入（两段会话）

之前「写入配方」只管颜色，「写入菜单文字」只管名字，于是会出现名字是富士、颜色还是原厂那种半套状态。这一版把它们合成一个动作：

**「一次写入：颜色 + 名字」**（自定义外观页新卡片，两个按钮）：

- 一次写入：先写四条 CP 色度记录（RAM），断开、等相机复位、再连上写 `/usr` 语言资源；命名方案决定文字，颜色固定是那四条配方。
- 一次还原：颜色写回出厂记录，语言资源写回基线（没有基线就改回出厂短名，界面照旧说明这一档不是逐字节还原）。
- 全程约 2 分钟，其中约 1 分钟是等相机复位；进度条会报「还要等 N 秒」，不用拔线。

**为什么一定要拆两次连接**：实测在一个会话里既写 CP 单元又写 145 KB 文件，第 13 次传输左右端点必挂（`Pipe error` / `No such device`），文件停在半截。所以这不是为了稳一点，是唯一能走通的做法。

**失败时说清楚停在哪**：

- 颜色段失败 → 整段停下，菜单文字一个字都不动；
- 文字段失败 → 保留已经写好的颜色，日志写「颜色已经写进相机了，可以单独点『还原本页外观』回滚」。

命令行同一件事：`python tools/bundle_apply.py --apply --preset zh --confirm yes-write`（还原用 `--restore`）。

另外把会话冷却的进度改成每 10 秒报一次剩余时间，末尾报「冷却结束，重新连接相机…」——以前等 50 秒是一段没有任何反馈的静默。

测试：`pytest tests -q` → 93 passed / 1 skipped（新增 `tests/test_bundle.py` 7 个用例，覆盖两段顺序、兜底预设、还原分支、两段各自的失败处理与摘要）。七页界面离屏渲染、冻结包九项自检均通过。

**未验证**：一次写入 / 一次还原的真实相机流程（本地测试只覆盖编排，不覆盖硬件）；`/setting/` 写入路径仍未被真机使用过。

## 0.3.4：两套命名方案、只读检查的状态码说清楚了、真机踩坑写进文档

这一版没有新功能模块，做的都是真机上撞出来的事情。

**菜单文字两套命名**：卡片里多一个「命名方案」下拉，随时切换、不用重连相机：

- 官方原名：Classic Chrome / Classic Neg. / Positive Film / Negative Film（不加品牌前缀，菜单宽度也不会挤）
- 中文简称：富士CC / 富士NC / 理光正片 / 理光负片

两套都能写、都能还原；切方案只影响「目标文字」，写了哪一版由文件里的实际内容判定，状态列会写清「已是目标文字 / 出厂短名 / 两条记录不一致」。

**只读检查报错不再只有一句泛化文案**：相机拒绝暂存配置或载荷时，现在会说明是 `配置写入（SET_FILE2）` 还是 `载荷写入（SET_FILE）`，并把状态字翻成人话（例如 `状态 0x10000004`：相机侧临时文件操作被拒，通常是上一次会话没干净结束），后面直接跟恢复步骤。之前界面只显示「文件写入或载荷执行失败，状态：04000010」，看不出卡在哪一步，也不知道该做什么。

**写入载荷的白名单加了 `/setting/`**：为「整单元写回 BACKUP.BIN」留了通路（目前只给 `/setting/BACKUP.BIN` 用，`/usr/`、`/cp/` 的既有路径不变）。这条路径尚未在真机上跑过，文档里标成未验证。

**真机经验写进文档**（`docs/VALIDATION.md`、`docs/AI-HANDOFF.md`、`docs/CC-CN-PLAYBOOK.md`、`docs/LOOKS.md`）：

- CP 色度改完要**正常关机、等满 1 分钟再开机**才会被相机写进 `/setting/BACKUP.BIN`；关机立刻开机看到的还是旧值。
- 写入中途掉线（`Pipe error` / `No such device`）之后，普通「关机再开机」不够，要**拔线 + 关机 + 取电池约 1 分钟**冷启动，否则下一次写入的第一个块就掉。
- 一次认证会话里不要既写 CP 单元又写 145 KB 语言资源文件，「名字+颜色一起写」必须拆成两个会话、中间留冷却。

测试：`pytest tests -q` → 86 passed / 1 skipped。

**未验证**：`/setting/` 写入路径；两套命名方案的中文版在真机菜单上的实际宽度（英文版已实测正常）。

## 0.3.3：菜单文字也能改、也能还原（自定义外观页）

之前「自定义外观」只改颜色记录，菜单上仍显示 PT / NT / VV / VV2；想换名字得走命令行 `tools/uxc_grow.py`，而且还原没有界面入口。

现在「自定义外观」页多一张「菜单文字」卡片：

- **写入**：把 PT / NT / VV / VV2 的显示名改成 富士CC / 富士NC / 理光PF / 理光NF（每个外观在语言资源里有两条记录，一起改，避免菜单与列表不一致）。
- **还原**：
  - 有整份基线时整份逐字节写回，回读 SHA-256 与基线一致才算完成；
  - 没有基线时只把文字改回出厂短名，并明说「文件字节与出厂不同」；
  - 卡片里的「基线」一行直接写清当前是哪一档，不含糊。
- **导入基线…**：手上有出厂 `*.uxc` 备份时可以指定；文件会先校验 magic / `kind=8` / 外观记录是否齐全，不合格直接拒收。
- **写入前自动存基线**：整份语言资源（约 142 KB）存进数据目录的 `looknames/`，索引记 sha256、字节数、来源与时间。
- **一次检测读两样**：「检测当前状态」现在只认证一次，同时读颜色记录与菜单文字（两次认证会让相机来回切模式，慢且容易卡在服务模式）。

为什么分成两张卡片：颜色是 CP 运行时的 RAM，关机才落盘；菜单文字是 `/usr/share/app/string_simplifiedchinese_f.uxc` 这个文件，一写就持久。两者的还原手段与风险等级不同，混在一起讲会让人误以为「点了还原就万事大吉」。

实现：新增 `src/a6700win/uxc.py`（UXC-v7 解码 / 就地改名 / 整块后移改名，索引表按新偏移重写）、`src/a6700win/looknames.py`（读写、分类、基线库、三档还原）、`tests/test_looknames.py`（纯逻辑用例，合成资源）。`docs/looks-profile.json` 增加 `menu_slot` / `menu_names`，`docs/LOOKS.md` 增加 7.1 节。

实测（离线，用出厂备份）：四个外观改名后 145,612 → 145,676 字节；再改回短名后与出厂文件**逐字节一致**（sha256 相同）。这一条只是本项目实测行为，不当承诺——整份还原仍然靠写入前保存的基线。

**未验证**：真实相机上的菜单文字写入与还原（需要相机切 MSC 并授权一次），本版只在离线资源上验证了编解码、改名幂等与往返一致性。

> 2026-10-25 真机补记：英文原名与中文简称两版都已写入并在相机菜单上确认显示正常，还原能回到出厂 145,612 字节 / `fe263360…`。详见「0.3.4」一节。

## 0.3.2：修复 0.3.1 的写入失败，以及只读检查、恢复、演示模式的阻塞问题

### 写入：0.3.1 里解锁和关闭一定会失败

报 `Request changes bytes outside available catalog-owned fields`、状态 `uncertain`。原因：0.3.1 新增的 inode 时间戳豁免把「清零时间戳的副本」当成了写入目标。`before` 是相机原始字节，`after` 里的时间戳已被清零，`device_protocol.request()` 用「只允许改目录字段」的掩码逐字节复核，把这 12 字节判成越界修改，在发任何 USB 数据之前整单拒绝。

处理：归一化只用于比对，返回写入目标前把 9 个守卫扇区里的时间戳按相机原值补回；mask、内容校验与其余字节的处理不变。用本机真机 dump 复算：旧实现被 `request()` 拒绝，新实现 138 扇区 / 333 字节、`request()` 接受。

### 只读检查报「USB 认证失败（正在寻找唯一的 MSC 相机…）」

这条错误发生在认证第一步：相机接口没有绑定 WinUSB 时 libusb 枚举不到设备，原来只在 12 秒后提示「确认 MSC、关闭 FTP」，把用户引向无关设置。现在：

- 认证前先用 SetupAPI 找 `0x0E76` / `0x047D`，发现已连接但驱动不是 WinUSB 就当场补绑（会弹管理员授权）；
- 仍然找不到时，把 Windows 实际看到的 Sony PID 与驱动写进错误，例如「0x0EA6 不是存储模式（多半是 MTP、PC 遥控或自动）」或「0x0E76 存储模式（MSC），驱动 usbccgp」；
- 恢复服务模式、补绑驱动会花掉时间，等待窗口在之后重新计算，不会一恢复完就超时。

### 其它阻塞与误报

- **恢复整份备份点不动**：只读检查后勾选是「尚未开启的功能」，相机全开时为空，上游 `reserve()` 在检查备份之前就抛「请至少选择一个功能」。现在预约前按「整份恢复」补齐选择。
- **自定义外观与只读检查抢设备锁**：只读检查或备份后会话保持打开，外观页再连同一台相机会报「本机已有相机工具运行」。现在外观页动作前先退掉旧会话。
- **演示模式启动检查必失败**：simulation 模式没装 Windows 补丁，`resources` 项在上游清单的 source_sha 不一致上永远失败。现在两种模式都装补丁。
- **结果页「返回功能管理」不跳转**：`call_controller(...) or goto(...)` 被返回值短路。
- **写前校验拒绝被报成「独立回读失败」**：设备返回 status=1 且零字节写入时归类为 `rejected`（写前校验拒绝），不再提示「不要盲目重试」。
- **退出服务模式确认**：接受 `0x047D` 作为正常的存储模式 PID，不再误报「无法确认退出服务模式」。
- **关窗口**：任务在 5 秒内没停下就不再强关，避免在写 USB 的过程中销毁会话。
- **驱动页**：没绑 WinUSB 时挡住「下一步」；安装程序返回成功但没观察到接口切换时，不再提示「已绑定」。
- **驱动安装超时**：父进程按 PID 数放宽等待，超时会终止提权子进程并单独报超时，不再报成「可能取消了授权」。
- **打包**：`build.ps1` 校验冻结包自检结果（失败即中止），支持绝对 `-DistPath`；`--render-pages` 默认使用系统字体目录，不再静默输出整页方框；数据目录可写性探测的临时文件按进程命名。
- **相机拒绝数据包时的提示**：`文件写入或载荷执行失败，状态：04000010` 这类错误现在会写清是哪一步（配置 `0x4010` / 载荷 `0x4007`）、file_id、状态码（如 `0x10000004`）和原始字节，并直接提示拔线、关机重开后再试。

测试：`pytest tests -q` → 75 passed / 1 skipped。

**未验证**：真实相机上的解锁/关闭与恢复写入（0.3.1 之后没做过实机写入）；只读检查的新驱动补绑路径也只在离线环境验证过。

## 0.3.1：驱动组件随包附带（不再依赖联网）

- libwdi 的 `wdi-simple.exe` 与 `amd64/`、`x86/` 驱动载荷打进安装包（`_internal/third_party/libwdi`，7.4 MB）；首次绑定驱动时由 `ensure_wdi()` 复制到数据目录的 `driver` 子目录，**完全离线**。之前国内网络打不开 GitHub Release、点「下载驱动组件」一直失败、卡在「缺少组件」无法绑定 WinUSB 的问题不再出现。
- 「下载驱动组件」按钮保留为兜底：只有包内组件被安全软件删掉时才用，且改为依次重试 `https://ghfast.top/`、`https://gh-proxy.com/` 两个反代；随包组件在时直接跳过网络。
- 冻结包自检的 `wdi` 项从「可选、失败不计入」改成必需项，缺组件会直接判自检不通过。
- 压缩包根目录新增 `必读.txt`（十节上手流程：解压、SmartScreen、驱动、四步功能、还原、常见问题）以及 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md`。
- `packaging/build.ps1` 支持 `-DistPath` / `-WorkPath`，程序正在运行时也能把新包构建到别处。

- **修掉「兼容性检查未通过 / blocked」误报**：/usr 分区里有 9 个结构守卫扇区落在 ext2 inode 表上，相机自己会刷新 inode 时间戳，导致什么都没做也判不兼容。现在只对这 9 个扇区的 atime/ctime/mtime（每个 inode 12 字节）放行，内容与其余字节仍逐字节校验。

边界：只能改颜色倾向，做不出富士的 S 形影调；`.cube` / `.dcp` 不能直接导入。

## 安装与运行

1. 解压 `Powerful6700-Windows-x64.zip`，得到 `Powerful6700` 目录（绿色版，无需安装）
2. 相机设为 **USB 连接模式 = 海量存储(MSC)**，关闭 FTP，接一根数据线且只接一台目标相机
3. 双击 `Powerful6700.exe`（首次绑定驱动建议右键「以管理员身份运行」）
4. 「操作前须知」：启动检查 → 勾选阅读确认 → 底部「下一步：驱动准备」
5. 「驱动准备」页：扫描设备 → 绑定 WinUSB（libwdi 组件随包附带，完全离线；0x0E76 首次绑定要 UAC；第一次只读检查时出现的 0x0336 会由程序自动绑定）
6. 「相机准备」四项确认 → 开始只读检查 → 「功能管理」勾选功能 → 解锁／关闭
