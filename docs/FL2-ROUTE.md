# FL2 / FL3 移植到 A6700：现状与结论

更新时间：2026-10-24　相机：ILCE-6700 / 固件 2.00　方式：静态反汇编 + 只读 dump + RAM 探测

> **2026-10-25 修订（重要）**：本文的「不可行」结论已被同机型项目 `Himpq/FireHydrant` 的真机结果推翻。
> 菜单文字仍不可得（这半条成立），但**功能可行**：复用两个自定义位（`selected = 14/15`）+ appFw `0x34E5604` 的 112 B 转换窗口 → CP mode 19/20，
> 配套 `/cp/cpapp-b.bin` 33 窗 delta 与 CP 单元空槽参数。完整方案与数字见 `AI-HANDOFF.md` §18；下文保留 2026-10-24 的原始判断，冲突处以 §18 为准。


参考实现：`refs/a7c2-fl23`（A7C2 / 固件 2.01 的 FL2·FL3 工具）。本文偏移都属于
`firmware/appFw-2.00.so`（89,027,992 B）与 `firmware/cp/cpapp-b.bin`（17,892,024 B，头部 `e59f1004`）。

## 0. 结论摘要

1. **颜色层可达但价值不足**：CP 单元 `0x02a40001` / `0x02a4000d` 的读写在真机上跑通，改完立刻可见、掉电恢复。
   但只改色度 / 矩阵 ≈ 相机内的「饱和度」滑块，用户当场判定「我在相机里也能改」。
2. **「菜单里出现 FL2/FL3 字样」仍不可行，但「FL2/FL3 功能」可行**（2026-10-25 修订，原判定只对了一半；2026-10-26 实测：条目已能多出两项、显示为 `5VV2` / `6BW`，功能侧在静拍上不成立）：外观资源 id 只有 1..11、
   显示文字不是明文——这部分成立。同机型项目已用另一条路做成：复用两个自定义位 → appFw `0x34E5604` 112 B 映射到 CP mode 19/20，菜单仍显示旧名。
3. **缺的不是 gamma，是「模式表 + 槽参数」**（2026-10-25 修订）：FL2/FL3 的观感由 cpapp 的 42 项 CP 候选模式表与 CP 单元里每槽 8 项参数
   （对比度/高光/阴影/褪色/饱和度/锐度/范围/清晰度）共同决定；A6700 的 9 条 1024 B gamma 斜坡确实是死数据，但它不是必要载体。
4. **「要新写窗口」不成立**：260 扇区 / 133,120 字节只约束 CP 单元与 SENSER 读；写文件走 `/usr/`、`/cp/`、`/setting/` 白名单
   （`native/flash_write.c`：任意偏移 + 自动 remount rw + fsync + 独立句柄回读），我们已用它单会话写过 145,708 B 的文字资源。
5. **修订后的完整方案**（三层落点、字节数、写序、禁区）见 `AI-HANDOFF.md` §18：C 层 CP 空槽 → B 层 `/cp/cpapp-b.bin` 33 窗（4,456 B）→ A 层 `appFw.so` 112 B。

## 1. 静态定位（已确认）

### 1.1 appFw：外观编号 → CP mode 转换器

- 函数序言 `0x34e54ac`，转换核心 `0x34e5604`（A7C2 对应 `0x3528804`，结构同构）。
- 代码：`cmp w1,#9` → `b.hi 0x34e5674`（打「非法外观」日志）→ `adrp x0,0x40b6000` + `add x0,x0,#0x24`
  → `ldrb w0,[x0,w1,uxtw]` → `adr x1,0x34e5624` + `add x0,x1,w0,sxtb #2` → `br x0`。
- 索引表 `0x40b6024`（10 项 ×4）：`12 00 02 04 06 08 0a 0c 0e 10`；`0x12` 指向默认块 `0x34e566c`
  （`strb wzr,[x2]; ret`）。
- 映射：**0→0、1→3、2→2、3→1、4→0x10、5→0x0f、6→0x11、7→0x12、8→5、9→0x0d**。
- A7C2 打过补丁的表是 `00 03 02 01 10 0f 11 12 05 0d 13 14`：**前 10 项与 A6700 逐项相同**，
  A7C2 只是把上限 9→11 并追加 mode 0x13 / 0x14。
- 该函数既没有 `bl` 调用者，也没有 rela addend / u64 指针指向它 → 只能被间接派发（别再用 bl 扫描找调用者）。

### 1.2 appFw：外观标签族与 16 个外观槽位

**（2026-10-24 纠正）** 这里原先写的是「`0x49e34d0` 起是 11 条外观记录表」，**这是错的**：`0x49e34d0` 的记录是 `RECORD_SETTING_600M_422_10BIT` … `150M_420_8BIT`，属于码率/记录设置表。

真正的外观标签在资源名字典里：

- `VAL_setting_creative_style_plus_CREATIVE_STYLE_PLUS_STANDARD` 的字符串在 `0x42087aa`，字面量槽在 **`0x4926e40`**（另有 `0x7e6620`）。从 `0x4926e40` 起是 16 字节记录 `{char* name, 0}`，依次是 STANDARD / PORTRAIT / NEUTRAL / VIVID / BRILLIANT / FILM / RETRO / AIRY / BLACK_WHITE / SEPIA，再接 CREATIVE_BOX 1-6、INVALID、PRM_ALL。
- 紧接着 `0x4926ed0` 起是 `VAL_creative_look_option_look0 … look15`，**每个 lookN 都带 10 个基础外观名**（16 组 × 10 = 160 条）；同族还有 `creative_look_option_{contrast,fade,clarity,fineness,…}0..15`。

→ **A6700 的数据模型是 16 个外观槽位**（10 基础 + 6 自定义），没有 look16 / look17；这与菜单里的 16 项（ST,PT,NT,VV,VV2,FL,IN,SH,BW,SE,1ST,2FL,3IN,4SH,5VV2,6BW）一一对应。`ICON_TOUCH_*_CREATIVE_LOOK_*` 那 11 条字符串没有重定位槽，只被 pcrel 引用（所以按指针 xref 找不到调用者）。

### 1.3 CP（cpapp-b.bin）：单元目录与初始化数据块

- 单元目录 `0xc2a5b0`，19 条 12 字节 `{u32 key, u32 RAM 地址, u32 size}`；同一目录在
  `nflasha8-2.00.bin` 的 `0xe765b0`（cpapp-b.bin 在分区里从 `0x24C000` 开始）。
- 初始化数据长度字段在 `cpapp 0x20140`，本机值 `0x001412B8`（全文件唯一），推得数据块
  **`[0xFBF000, 0x11002B8)`**，其后还有 `0x10000` 字节全零尾块可作追加空间（与 A7C2 的改动位置同构）。
- 两个颜色单元在静态镜像里**全 0** → 颜色 / 矩阵是 CP 启动后填充的 BSS，静态镜像没有可复制的字节
  → 只能走运行时 `cp_read` / `cp_write`。

### 1.4 CP：32 路「外观类别 → 参数」填表函数

- `0x135b30`：`push {r4,r6,r7,lr}` → `ldrd r3,lr,[r0]` → `ldrb.w r2,[r3,#0x2e]`（键）→ `subs r0,r2,#1`
  → `cmp r0,#0x1f` → `bhi 0x135c54` → `ldrb.w ip,[r3,#0x17]` → `tbh [pc,r0,lsl#1]`，跳表基址 `0x135b4c`。
- 键 15/16/17/18（CP mode 0x0f/0x10/0x11/0x12）→ 参数 `0x2d`/`0x2e`/`0x2f`/`0x30`（45..48）。
- 键 19/20（mode 0x13/0x14）→ 处理块 `0x135c9e` / `0x135cb0`（`movs r0,#4` / `#5` + `strb r0,[r1,#2]`，
  随后 `movw r0,#0x1094; movt r0,#0x16f` 读单元 `0x02a40001`）→ **这两个 mode 的调度入口在 A6700 CP 里已存在**。
- 调用者只有两处：`0x135084`、`0x1350e6`，都在 `0x1350xx` 的外观参数解析函数内。

单元内布局（与 A7C2 模型一致）：

- `0x02a40001`：参数表 `0x1200`（1 B/参数）；chroma 记录 `0x1250 + 槽×64`，每条 32 int16 =
  **24 个有效 + 尾 8 个 0**（对应 donor 的 `cc1_int16` 3×8）。可用槽数 `(8192-0x1250)/64 = 54`，
  末尾 48 字节不可用；实际非零的色度槽：**0..21、28、29、32..39**。
- `0x02a4000d`：参数表 `0x196`；矩阵记录 `0x1e0 + 槽×768`（前 576 B = 3 端点 × 16 × 6 int16）。
  实际在用的矩阵槽：**0..19、32、33**，20..31 全零。

参数表前 52 字节（unit01 @0x1200）：

```
00 02 04 00 00 00 06 02 00 00 01 00 20 11 12 22 22 22 13 25 21 01
03 05 00 00 00 07 03 00 00 26 20 11 12 23 23 23 13 25 10 08 0e 0a
0c 09 0f 0b 0d 13
```

- 索引 45..48 = `09 0f 0b 0d`，正好对上「mode 0x0f..0x12 → 参数 45..48」。
- 两个单元在索引 41..48 上完全相同：`41..48 = 8,14,10,12,9,15,11,13`；索引 23 = 5（VV2）、41 = 8（FL）、45 = 9（SE）。
- 因此参数值是**整族编号**、两个单元共用，不能直接当作「各自单元的槽号」。

> 语义提示：`cp_write` 后 `cp_read` 立刻一致，说明这两块是**活的 RAM**；发 `STOP_SENSER`、拔插 USB、
> 重新枚举成 `0x0E76` 之后内容仍保留，只有真正掉电（关机 / 取电池）才回原厂。
> 所有 RAM 探测因此可以连续做，不必每次重写。

## 3. 真机探测：槽号归属（路线 C 的成果与边界）

工具：`tools/cp_write.py`（单单元、`--keep-service`）、`tools/cp_patch.py`（一次会话连写多个单元，
自动留 `.orig`、回读比对）。所有探测只改 RAM，掉电恢复。

| 探测文件 | 改动 | 机身观察 |
| --- | --- | --- |
| `unit-02a40001.chroma_zero.bin` | 全部 32 个色度槽清零 | 所有外观都变灰（CP 色度表是活的） |
| `unit-02a40001.zero9.bin` | 只清零槽 9 | **SE 变灰** |
| `unit-02a40001.zero11.bin` | 只清零槽 11 | 看不出变化 |
| `unit-02a40001.zero5.bin` | 只清零槽 5 | **VV2 变灰** |
| `unit-02a40001.tri_678.bin` | 槽 6 ×4 / 槽 7 取反 / 槽 8 清零 | **PT 变艳、FL 与 2FL 一起变黑白** |
| `unit-02a40001.fl2_at_slot8.bin` + `unit-02a4000d.fl2_at_slot8.bin` | 把 FX2 donor 的 FL2 写进槽 8（色度 + 矩阵） | 肉眼无差别（拍 FL 对比确认） |
| `unit-02a4000d.zero_matrix8.bin` | 矩阵槽 8 全 0 | 只有饱和度变化，颜色没塌 |

实测槽位归属：**槽 5 = VV2、槽 6 = PT、槽 8 = FL（2FL 与它绑在同一组参数上）、槽 9 = SE**。
用户给出的相机菜单顺序（16 项）：`ST, PT, NT, VV, VV2, FL, IN, SH, BW, SE, 1ST, 2FL, 3IN, 4SH, 5VV2, 6BW`。

**边界**：把 FL 槽换成 FX2 的 FL2 donor 数据后没有可见差异；矩阵槽归零也只是饱和度变化。
用户结论：这一层能做的等价于相机内可调项（对比度 / 高光 / 阴影 / 褪色 / 饱和度 / 锐度 / 锐度范围 / 清晰）。

## 4. 标签不可得（这半条仍成立：改名可以，新增不行）

### 4.1 资源 id 表没有空位

见 §1.2：外观 id 只用 1..11，`0xc` 已被 `BASE_ISO_SENSITIVITY_DISPLAY_ON` 占用。想新增一项
外观，必须先有可用的 id 与其文本资源。

### 4.2 显示文字不是明文（全机身扫描）

| 范围 | 大小 | 结果 |
| --- | ---: | --- |
| `appFw-2.00.so` | 89 MB | `FL2`/`FL3` 0；`Sepia`/`SDXC`/`Creative Look` 0；中文 UTF-8 密集串 0 |
| `nflasha5-2.00.bin`（WBI） | 314 MB | 同上，全部 0 |
| 其余 13 个分区（除 WBI 外全部，含 CP 与 nflasha15） | 1.30 GiB | 同上，全部 0 |

补充证据：appFw 里 zlib 候选流 3,756 个位置，解压成功 **0** 个；UTF-16LE 的 `VV2`/`Standard`/`Sepia` 也 0 命中。
→ 菜单文字存放在**不可读写的资源包**里。

### 4.3 A7C2 为什么能显示

`refs/a7c2-fl23/src/camera_runtime/assets/patches.json` 里 8 处 appFw 写入全部是开关位 / 映射表 / 槽位绑定
（转换器、两个 selection capability、Fade 默认、槽 16/17 绑定、两个菜单 product flag），**没有一处写文本**
→ A7C2 固件出厂自带 FL2/FL3 的 id 与标签，工具只是把锁打开。A6700 没有这两把锁。

**判定（2026-10-26 真机更新）**：菜单里**确实能多出两个条目**（我们已把它做成 16 项，新增项显示为 `5VV2` / `6BW`），但「叫 FL2/FL3」这个名字仍然写不上去；真正的死结不是名字而是：新条目只是基底外观的别名，静拍路径上没有可用的 mode 数据。下面这段只对「名字」成立；能做到的是**让某个已有外观在像素上像 FL2**（或复用两个自定义位），
名字仍然是现成标签。

**（2026-10-25 修订）后半句已被真机做成**：复用两个自定义位 + appFw `0x34E5604` 的 112 B 转换窗口 + `/cp/cpapp-b.bin` 33 窗 delta
+ CP 空槽参数，菜单文字仍是旧名。方案见 `AI-HANDOFF.md` §18。

## 5. 自定义外观设置的落盘位置（两轮全分区 diff，未定位）

做法：用户在相机里把 `2FL` 八个参数全部拉到 9 → dump 全部分区（ext 态）；再调回默认、关机重开 →
再 dump 一遍（def 态）；逐分区对比。工具 `tools/dump_parts.py`，镜像在 `firmware/parts/<part>-{ext,def}.bin`。

| 分区 | 差异 | 性质 |
| --- | ---: | --- |
| nflasha5（WBI） | 0 B | sha256 前后完全一致 `56e0e220…` |
| nflasha8（CP） | 0 B | sha256 前后完全一致 `3bddcce3…` |
| nflasha10 | 534 B | 指针表 / 运行痕迹 |
| nflasha2 | 4,161 B | UPDATER 区重写 |
| nflasha6 | 变化 | JIT 缓存 |
| nflasha11 | 38 B | 计数器 |
| nflasha15 | 未全量 dump | 头部 cramfs + gzip，是固件镜像 |

结论：**没有找到任何 look 参数记录**；参数落盘位置仍未定位（可能在加密资源区内）。

补充（2026-10-24）：后来又做了一组「CP 单元级」对比 —— 把 `2FL` 八个参数拉到 9（ext）与调回默认（def）两份 nflasha2 里的 `BACKUP.BIN` 逐单元比对，19 个 CP 单元**全部 0 字节差异**（总差异 1,975 B 全在单元区之外）。
→ 外观参数既不在 CP，也不在上面这些分区里；唯一没全量 dump 的是 **nflasha15**（749,731,840 B），而相机根目录存在 `setting/`，`/usr` 又确认是 nflasha15 的根分区 → 参数最可能在 nflasha15 里。详见 `docs/PERSIST-STORE.md`。
因此「把 FX2 数据注入自定义位」这条路暂时没有落点。

> **2026-10-25 修订**：「没有落点」已不成立——同机型项目把 donor 数据落在 **CP 单元空槽**（`0x02A40001` chroma 槽 23 的 71 B、`0x02A4000D` matrix 槽 25 的 840 B，由参数表 `0x1200` / `0x196` 引用）+ `/cp/cpapp-b.bin` 33 窗 delta，`saveBackup(0x02a4)` 落盘。§5 的「19 个 CP 单元 0 差异」只说明**机身可调的八项参数**不在 CP，不说明 look 参数不在 CP。见 `AI-HANDOFF.md` §18.3。

## 7. 路线判断（2026-10-25 重写）

- **路线 A（完整移植）→ 已改名为「三层移植」，技术路径已通**：不新增外观枚举、不动菜单文字。
  C 层写 CP 单元空槽（chroma 槽 23 的 71 B + matrix 槽 25 的 840 B，`saveBackup(0x02a4)` 落盘）→ B 层写 `/cp/cpapp-b.bin` 33 个窗口（4,456 B，需完整断电）
  → A 层写 appFw `0x34E5604` 112 B（`selected = 14/15` → CP mode 19/20，冷启动生效）。写序 C → B → A。
  原「阻塞」逐条状态：① 文字仍不可得（改名可以，新增不行）；② 已定位（`0x34E5604` / `0x40B6024` / 16 槽标签族）；
  ③ 不成立（影调靠 cpapp 42 项模式表 + 槽参数，gamma 斜坡不是必要载体）；④ 不成立（写文件走白名单，不受 260 扇区限制）。
- **路线 B（只让已有外观在像素上像 FL2）**：被路线 A 吸收——A 层的 112 B 就是「把自定义位指向 CP mode 19/20」。
- **路线 C（只改 RAM 颜色表）**：已完成并验到边界 —— 只动色度一层时等价于机身饱和度，价值不足。
- **路线 C′（RAM tone 曲线）**：需要 RAM 注入通道（写 `/tmp/jiritsu/libJit.so` 触发 `dlopen`）；我们没有这条通道，且它断电即消失、不持久。

> 2026-10-25 补：§1.1 第 28–29 行记的 A7C2 补丁后索引表 `00 03 02 01 10 0f 11 12 05 0d 13 14` 就是 A 层要写的那 12 B —— 我们早就抄下来了，只是当时没意识到可以直接照搬。

## 9. 下一步（2026-10-24 的原计划，已被 §18.6 取代，保留作历史）

**0. 先全量只读 dump nflasha15**（749,731,840 B，约 3-4 分钟，无风险）——外观参数与 `.uxc` 资源的实际落点都在它的 ext2 文件系统里；`firmware/parts/nflasha15-head.bin` 只有前 4 MB，不够用。落盘后先在 `/setting` 与 `/usr/share/app` 里找落点，再决定是否需要写 flash。

**CP tone 单元定位实验**（需要用户看相机屏幕配合）：

1. 把 19 个单元里所有未知单元（`0x02a40000/02/04/05/06/08/09/0b/0c/0e/0f/11`）整体压扁（数值减半），
   观察画面是否出现**对比度 / 层次**变化（不是颜色变淡）——用来判断「CP 里到底有没有 tone 载体」；
2. 若有变化，按位数二分（先一半、再四分之一）锁定具体单元；
3. 锁定后把 FX2 donor 的 gamma 曲线按该单元的量化格式灌进去，做「像素上像 FL2」的外观。

判据：**能在不改 flash 的前提下让某个外观出现与 FL2 同向的色调/层次差异**。
若三σ内无变化，则 CP 里没有 tone 载体 → 只能回到路线 B（新写窗口 + cpapp 静态定位），风险与周期都上一个量级。
