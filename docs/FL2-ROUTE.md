# FL2 / FL3 移植到 A6700 的可行性现状

> 只读静态分析记录。所有偏移均指 `firmware/appFw-2.00.so`（89,027,992 B）与
> `firmware/cp/cpapp-b.bin`（17,893,048 B）。尚未对相机写入任何内容。

## 1. 已确认（本机实测 + 静态定位）

### appFw：外观编号 → CP mode 转换器已定位
- 函数序言 `0x34e54ac`，转换核心 `0x34e5604`（A7C2 对应 0x3528804，同构）。
- `cmp w1,#9` → 越界跳 `0x34e5674`（写日志）→ 表 `0x40b6024`（10 B）→
  `adr x1,0x34e5624; add x0,x1,w0,sxtb #2; br x0` 进各处理块。
- 表内容 `12 00 02 04 06 08 0a 0c 0e 10`；映射 **0→0, 1→3, 2→2, 3→1, 4→0x10,
  5→0x0f, 6→0x11, 7→0x12, 8→5, 9→0x0d**；0x12 指向默认块 `0x34e566c`
  （`strb wzr,[x2]; ret`）。
- 与 A7C2 打过补丁的表 `00 03 02 01 10 0f 11 12 05 0d 13 14` 前 10 项逐项相同；
  A7C2 只是把上限 9→11 并追加两个 mode（0x13 / 0x14）。

### CP：单元体系同源，但颜色数据是运行时生成
- 单元目录 `0xc2a5b0`（19 条 12 B：`{key, RAM 地址, size}`）：
  `0x02a40001 → 0x016f1094 / 0x2000`、`0x02a4000d → 0x016f3594 / 0x7000`，
  与 A7C2 的 8192 / 28672 完全对上。
- 初始化数据长度字段 `cpapp 0x20140 = 0x001412B8`，数据块 `[0xFBF000, 0x11002B8)`，
  其后 0x10000 全零尾块可作追加空间；与 A7C2（0x1100b80 追加、长度改 0x142aa0）
  的块首 0xFBF000 一致。
- 但两个颜色单元在镜像里**全 0**：颜色/矩阵是 CP 启动后填充的 BSS，静态镜像
  里没有可复制的字节 → 必须走运行时 `cp_read` / `cp_write`。

### CP：有一个 32 路的「外观类别 → 参数」填表函数
- `0x135b30`：`ldrb.w r2,[r3,#0x2e]`（键 1..32）→ `tbh` 跳表 `0x135b4c`
  （32 个半字偏移）→ 每个处理块把 `{字节, …}` 写进 `sp+0x10` 的 16 B 记录。
- 键 19（0x13）/ 20（0x14）的处理块存在（`0x135c9e` / `0x135cb0`，写 `[r1,#2]=4/5`
  后读 CP 单元 `0x016f1094`），即这两个 mode 的**调度入口在 CP 里已经存在**。
- 调用者只有两处（`0x135084`、`0x1350e6`），都在 `0x1350xx` 的外观参数解析函数内。

### 关键负面结论
- `FL2` / `FL3` 字符串在 appFw 与 cpapp 里 **0 命中**；`Fade` 只有零星普通串。
  → A6700 固件里没有 FL2/FL3 的标识，也没有可复用的两个新名字。
- `cmp #0x2f`（A7C2 把上界改到 0x32 的那条）在 cpapp 有 53 处，形似「参数表上界」
  的是 `0x280352`（`cmp r0,#0x2f; bgt` 后 `ldr [0x017faae0 + r0*4]`），
  但没有旁证确认它就是 gamma/参数表；不确认就改 = 赌博。

## 2. A7C2 的四层做法（对照）

1. appFw 只「开门」：上限 9→11 + 12 字节表 + 两个选择能力 + Fade 默认 +
   槽 16/17 绑定（0x4b4a5e4/0x4b4a5ec = 10/11）+ 两个菜单产品标志（0x59892ca/0x5989382）。
2. cpapp 扩容量：数据长度 0x141b80→0x142aa0（+3872 B），并在 0x1100b80 追加
   curve/gamma/mode 表，gamma/模式表指针改到新地址（RAM = 文件偏移 + 0x108900）。
3. 运行时用 `cp_read` / `cp_write` 把 FL2/FL3 的 chroma(64 B)/矩阵(576 B)
   写到参数 55/56、槽 23/25（单元 0x02a40001 / 0x02a4000d）。
4. 数据来自 FX2 固件的 donor（`assets/fx2_fl23_donor.json`），带版本/哈希门禁与回滚。

## 3. A6700 缺什么（按阻塞顺序）

| 层 | A6700 现状 | 缺口 |
| --- | --- | --- |
| appFw 转换器 | 已定位，上限 9 | 改上限 + 追加 2 项表（可直接做） |
| appFw 外观定义/菜单门 | 未定位 | 需要找到「外观数量」与槽位绑定表 |
| appFw 标签资源 | 无 FL2/FL3 串 | 新外观没有名字，只能复用现有标签 |
| cpapp 参数槽 | 未见 55/56 | 需要扩参数表 + 追加记录（A7C2 抬了 3872 B） |
| cpapp 矩阵/chroma 白名单 | 未定位 | 新参数要能走主 chroma 图与矩阵表 |
| 运行时写单元 | 已有只读 dump 通道 | `cp_read`/`cp_write`（0x4010/0x4007/0x4008 + CP key）尚未实现 |

## 4. 三条路线

- **路线 A：完整移植（对齐 A7C2）**——把上面六层全打通。代价最高，其中
  「appFw 外观定义表」与「cpapp 参数表」两处未定位，且新外观无标签（会显示空名或
  复用相邻标签）。风险：写窗口要重做 catalog（结构守卫），没有真机旁证。
- **路线 B：只加两个「无名」外观**——先做 appFw 转换器 + 外观数量，把第 11/12 项
  指到已有 mode（例如复制 FL 与 IN 的 mode），验证菜单是否能多出两项。改动小、
  可回退，但看到的是已有颜色，不是 FL2/FL3 的新颜色。
- **路线 C：把颜色写进已有外观**——不动外观数量，用运行时 cp_write 把某个现有
  外观（如 FL）的 chroma/矩阵替换成 FX2 的 FL2 数据。用户看到的是「FL 换了颜色」，
  没有新增菜单项；技术上最接近当前已有能力（只读 dump 通道已通）。

## 5. 建议顺序

1. 先做**路线 C 的技术验证**：实现 CP 单元 `cp_read`/`cp_write`（只读写 0x02a40001 /
   0x02a4000d 两块 RAM），读出本机 FL 的 64 B chroma 与 576 B 矩阵，确认我们能在
   不写 flash 的前提下改内存中的颜色表并观察机身效果（掉电即恢复）。
2. 路线 C 成立后，再评估路线 A 的两处未定位表；否则完整移植没有落地条件。

## 6. 待验证的开放问题

- CP 单元读写是否需要额外的权限/命令（A7C2 用 `cp_read`/`cp_write`，A6700 的
  transaction.elf 目前只暴露 0x4010/0x4007/0x4008 三条）。
- 0x280352 的 `cmp #0x2f` 是否为参数表上界。
- 32 路填表函数的键到底是不是 CP mode（需追 `struct+0x2e` 的写入点）。

## 7. 真机读取成功（路线 C 第一步已通过）

工具：`tools/cp_read.py`（只发 0x603/0x40 读，含 CP 读特有的 0x200 结束包处理）。
相机在 MSC（0x0E76）→ 自动切服务模式（0x0336）→ 读取 → STOP_SENSER。

- `0x02a40001`：8192 B，非零 2815，sha256 `91d5e04018cacae6afa1e16c19157ebcd72c7833a5de0d0c220bc963c22c066c`
- `0x02a4000d`：28672 B，非零 8752，sha256 `64ceb9aa0279493eff598cc37e024b51e1573f678f73bdaf2c878f6147d9b209`
- 落盘：`firmware/cp/unit-02a40001.bin`、`firmware/cp/unit-02a4000d.bin`

### 布局与 A7C2 模型一致
- 单元 0x02a40001：参数表 `0x1200`（1 B/参数）；chroma 记录 `0x1250 + 槽×64`，
  每条 32 个 int16 = **24 个有效 + 尾 8 个 0**，与 donor 的 `cc1_int16`（3×8）形状完全对应。
- 单元 0x02a4000d：参数表 `0x196`；矩阵记录 `0x1e0 + 槽×768`（前 576 B = 3 端点 × 16 × 6 int16）。
- 实际在用的矩阵槽：**0..19 与 32、33**；20..31 全零。

### 参数表实测（0x02a40001 @0x1200，前 52 字节）
```
00 02 04 00 00 00 06 02 00 00 01 00 20 11 12 22 22 22 13 25 21 01
03 05 00 00 00 07 03 00 00 26 20 11 12 23 23 23 13 25 10 08 0e 0a
0c 09 0f 0b 0d 13
```
索引 45..48 的值正好是 `09 0f 0b 0d`，而 cpapp 那个 32 路填表函数把
mode 0x0f/0x10/0x11/0x12 映射到参数 0x2d/0x2e/0x2f/0x30（45..48）。
→ **候选链条：外观 → mode → 参数号 → 参数表里的字节 → 矩阵/chroma 槽号**。

### 下一步实验（RAM 写入，掉电即恢复）
1. 写 `tools/cp_write.py`（已写好，含 .orig 备份与回读校验）。
2. 用一次可见的探测确定槽位归属：把某个槽的 chroma 改成全 0（去色），
   问用户「哪个外观变了」→ 反推槽号。
3. 确认槽号后，把 FX2 donor 的 FL2 数据写进该槽，验证颜色生效，再谈固化。

## 8. 真机探测结果（路线 C 的边界）

- CP 色度/矩阵表是**活的**：只读 dump → 改 → 写回 → 相机画面立刻变（无需固件写入，掉电即恢复）。
- 实测槽位归属（色度表 unit 0x02a40001，0x1250 + 槽×64）：
  - **槽 5 = VV2**（归零后 VV2 变灰）
  - **槽 8 = FL**（归零后 FL / 2FL 一起变灰，说明自定义位绑在同一组参数上）
  - **槽 9 = SE**（归零后 SE 变灰）
- 但这层能改的只相当于相机内的「饱和度」滑块：把槽 8 换成 FX2 的 FL2 donor 数据，
  肉眼几乎无差别；用户当场指出「这个我在相机里也能改」。
- 参数表（unit01 @0x1200 / unit0d @0x196，200 项内）在索引 41..48 处两个单元完全一致：
  `41..48 = 8,14,10,12,9,15,11,13`，正是 10 个基础外观那一族；索引 23 = 5（VV2）、45 = 9（SE）。
- 结论：**光改 CP 内存里的色度/矩阵，等价于相机内可调项，产品价值不足**。
  真正的 FL2/FL3 需要 A7C2 那套四层移植（appFw 开菜单口 + cpapp 扩数据 + 运行时写槽 + donor 数据），
  其中 gamma 曲线与模式表指针都在 cpapp-b.bin（flash），必须新开写窗口。

## 9. WBI（nflasha5）dump 与「自定义外观位」的落点

- 只读 dump `/dev/nflasha5` → `firmware/nflasha5-2.00.bin`，314,572,800 B，
  sha256 `56e0e220cf0956f2ee8d524a8b805c4da8f700b40ce667f63151d00f4eecb2ab`（82 s，3,746 KiB/s）。
- WBI 是 blob 容器（头 `WBI2`），里面有按名字注册的资源 blob。与外观相关的名字：
  - `CREATIVE_STYLE_PLUS_{STANDARD,VIVID,NEUTRAL,PORTRAIT,FILM,SEPIA,RETRO,AIRY,BRILLIANT,BLACK_WHITE,INVALID}`
  - `CREATIVE_STYLE_PLUS_CREATIVE_BOX_1..6` ← **就是菜单里的 1ST/2FL/3IN/4SH/5VV2/6BW 六个自定义位**
  - `ICON_TOUCH_FUNCTION_AUTO_CUSTOMIZE_CREATIVE_LOOK_*`、`CINEMATIC_MODE_LOOK_*`
- 菜单缩写 ↔ 固件枚举（appFw 名字表 0x36531c8 起，顺序）：AUTO / STANDARD=ST / PORTRAIT=PT /
  NEUTRAL=NT / VIVID=VV / BRILLIANT=VV2 / FILM=FL / RETRO=IN / AIRY=SH / BLACK_WHITE=BW / SEPIA=SE。
- **显示文字拿不到**：`FL2`/`FL3` 在 appFw、cpapp、nflasha8、nflasha5 里全 0 命中；
  U+UTF-16 的 `VV2`/`Standard`/`Sepia` 也全 0 → 文本是打包压缩的 UI 资源（bci BlobWrapper / boost interprocess），
  要新增或改名必须先解这个容器格式。
- 结论：
  - 「颜色像 FL2」可达：往 `CREATIVE_BOX_n` 注入 FX2 的 FL2 数据（持久，掉电不丢），但菜单名仍是 `2FL`。
  - 「菜单出现 FL2/FL3 字样」需要解 UI 文本资源包，是独立攻坚项。
- 下一步（只读差分）：让用户在相机里编辑某个自定义位（对比度/饱和度/褪色拉满）→ 再 dump 一次 WBI → diff 出 box 数据块偏移与字段布局。

## 10. 自定义外观设置的存储位置排查（第一轮）

- 用户在相机里把 `2FL` 自定义位调到极端（对比度/高光/阴影/褪色/饱和度/锐度/锐度范围/清晰 = 9）后：
  - `nflasha5`（WBI）**sha256 与改动前完全一致**（56e0e220…）→ 设置不在 WBI。
  - `nflasha8`（CP）**sha256 与之前 dump 一致**（3bddcce3…）→ 设置不在 CP。
- 分区枚举（`/dev/nflashaN`，stat 只读）：0/9/14/16/17/19/20 不存在；
  1=25,100,288 / 2=20,971,520 / 3=78,643,200 / 4=12,582,912 / 5=314,572,800 /
  6=26,214,400 / 7=16,777,216 / 8=67,108,864 / 10=12,582,912 / 11=314,572,800 /
  12=41,943,040 / 13=4,194,304 / 15=749,731,840 / 18=20,971,520。
- 除 15（appFw，749 MB）外全部已 dump 到 `firmware/parts/*-ext.bin`（ext=极端参数态）。
  其中 1/2/6/10/12/13/18 是 mkdosfs FAT 卷（含 /etc、UPDATER、APPFW_*、IMAGES、HASH/HISTORY 等目录），
  4 与 7 不是 FAT。
- 下一步：需要「默认参数态」基线 —— 用户把 2FL 调回 0、关机重开、重新连接，
  再 dump 同一批分区做 diff，即可定位保存位置与偏移。
