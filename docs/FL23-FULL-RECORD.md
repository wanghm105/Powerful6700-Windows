## 1. 一句话现状

## 3. 相机侧机制：四层结构

一个「外观（look）」= **模式数据 + 矩阵 + 色度 + 8 项参数**，再加上显示名。四层各在不同文件里：

### 3.1 A 层：`/usr/lib/appFw.so`（89,027,992 B，sha256 `721fceae…`）

RVA `0x34E5604` 起 112 B 的「选择器」，把「选中项 + 基底外观」翻译成一个字节的**模式号**写进 `[x2]`。

原厂函数入口 `0x34E55F0`：

```
cmp  w0,#0x10        ; w0 = 菜单序号（0..15）
b.ne 0x34e5604
mov  w0,#-1          ; 只有 0x10 这一支存 0xFF
strb w0,[x2]
ret
```

主路径 `0x34E5604`：`cmp w1,#9` → `b.hi 0x34E5674`（越界走诊断打印）→ 查 `0x40B6024` 的 10 字节表 → `adr x1,#0x34E5624` → `add x0,x1,w0,sxtb #2` → `br x0`。表 `0x40B6024` = `12 00 02 04 06 08 0a 0c 0e 10`；桩在 `0x34E5624` 起每 8 B 一个，依次 `mov w0,#3 / #2 / #1 / #0x10 / #0xf / #0x11 / #0x12 / #5 / #0xd`，最后 `strb wzr,[x2]; ret`。

**`w1` 是基底外观编号**，`w0` 是菜单序号。这就是整个战役最贵的一行：**FireHydrant 的 112 B 补丁只在 `w1 == 0`（基底 = ST）时接管**。六个自定义槽的显示名是「序号 + 基底名」，实测 `5VV2` 的基底是 VV2（`w1 = 4`）→ override 从未触发；槽 1 现在显示 `1FL`（基底 FL），所以「哪个槽的基底是 ST」这件事必须先用真机确认（§13 第 8 条）。

base → mode（修正后的解，上一版算错过一次）：**ST 0、PT 3、NT 2、VV 1、VV2 16、FL 15、IN 17、SH 18、BW 5、SE 13**。

调用点只有两处：`0x34f33d4`（w0/w1 取自 `[x19+0xf0]`，结果写 `x20+0x1c8`）与 `0x34fdeb0`（把结果塞进 12 字节 settings 元素：`+0x30`=tag 5、`+0x32`=id `0x402f`、`+0x34`=value dword、`+0x38`=mode 字节，以 `w0=0x90030001` 调 `0x34f2360` 交成像管线）→ **mode → 记录的换算在管线侧**。

### 3.2 B 层：`/cp/cpapp-b.bin`（17,892,024 B，sha256 `43c5d056…`）

`cp.delta` 33 个窗口，magic `A6700D01`、version 1、count 33、payload 8,912 B、窗口表在 `0x60`、payload 起 `0x270`。实写 **4,456 B**，实际变化 **2,080 B**。

五个 4 B 指令窗（每个只变 1 字节）：

| 偏移 | 原指令 | 补丁后 |
|---|---|---|
| `0x317C70` | `msub w0,w22,w13,w28` | `…w29` |
| `0x318596` `0x3185E4` `0x9B2DA6` | `add w0,w22,#0x37c` | `#0x77c`（结构放大 0x400） |
| `0x3186C6` | `adr x0,#0x33451E` | `#0x35451E`（表基址 +0x20000） |

三处 `cmp r7,#0x2f` → `#0x32`（`0x317A68` / `0x317A84` / `0x9B2D6C`）：外观号上限 47 → 50。

两张表：

- `0x10D11D8`，**168 B = 42 项 u32 模式表**。出厂全零；打完补丁成对出现 `0,10,0,10,…`，19/20 项填 `26`。
- `0x10D02B8`，**3,872 B 模式数据本体**（音调斜坡）。出厂全零；补丁后是 968 个 u32 单调递增到约 130000 的凸曲线（1,682 个非零字节）。

还有两个名字槽：`0x1474F8` = `FL2`、`0x147508` = `FL3`（各 16 B），前面 27 B 表 `69 67 64 61 5e 5d 5b 59 57 55 52 4e 69 4c 5d 4b 49 48 47 0c 10 69 69 69 69 69 69 5d`。

`selector0` 在 `0x135F0A`，2 B：`00 20`（`movs r0,#0`）→ `00 BF`（`nop`），把 movie-only gamma shim 的归一化 NOP 掉。**只能打在 FL23 基线之上**（原厂那里是 `c0 f2`）。

### 3.3 C 层：CP 单元里的颜色参数

FireHydrant 只写 911 B：色度 `0x02A40001` **71 B → 槽 23**，矩阵 `0x02A4000D` **840 B → 槽 25**；每槽 8 项参数验收值 `0 0 0 1 0 4 3 1`（对比度 0、高光 0、阴影 0、褪色 1、饱和度 0、锐度 4、范围 3、清晰度 1）；写后走 `saveBackup(0x02a4)` 落盘。**字节不在该仓库里**，只有参数描述。

### 3.4 显示名：`/usr/share/app/string_simplifiedchinese_f.uxc`

三态实测：

| 来源 | 大小 | sha256 前缀 | 内容 |
|---|---|---|---|
| 索尼出厂 | 145,612 B | `fe263360c15b5530` | 短名 `PT` / `NT` / `VV` / `VV2` |
| 本项目 official 预设 | 145,708 B | `9fd0bb4971713fd9` | `Classic Chrome` / `Classic Neg.` / `Positive Film` / `Negative Film` |
| 本项目 zh 预设 | 145,692 B | `4a2a05e814a0ea3a` | `富士CC` / `富士NC` / `理光正片` / `理光负片` |

**「出厂原本就是短名」**——用户多次觉得「名字没变」，其实当时就是出厂态。当前 UXC 已写回出厂（145,612 B / `fe263360`）。

外观名 rid：ST `0x021C658E`、PT `0x021C6654`/`0x021C6F8B`、NT `0x021C6434`/`0x021C7002`、VV `0x021C687B`/`0x021C6F80`、VV2 `0x021C689A`/`0x021C6F4D`、FL `0x021C6CC9`、IN `0x021C6857`、SH `0x021C6961`、BW `0x021C65F8`、SE `0x021C658A`。

**自定义槽的显示名是运行时拼的**：「序号 + 基底外观名」。证据：把槽 1 的基底改掉后菜单从 `1ST` 变成 `1FL`、`2FL`；UXC 里搜不到 `1ST` / `5VV2` / `6BW`。

### 3.5 appFw 里那张 160 B 的外观记录表（走错的路，留作路标）

`0x04b597ac`，16 条，STRIDE 160：`+0x00` 名字 rid、`+0x08` 引导语 rid、`+0x10`=0x42b、`+0x14`=0x101、`+0x44`=条目序号、`+0x9c`=0x6ac+序号、`+0x7c` 指向 16 个 ARM64 getter 桩（`ldrb w20,[x0,#9+i]`）。

**改这张表的第 15/16 条（写 `FL2`/`FL3`）冷启动后菜单毫无变化**——它是「外观参数页」的条目，不是列表名来源。已按要求全部还原（`CUSTOM_NAME=0x021C6C81` / `CUSTOM_GUIDE=0x021C634A`）。

## 4. 已确证的事实（带数字与偏移）

### 4.1 CP 色度单元 `0x02A40001`（8,192 B）

- 参数表 `0x1200..0x1250`；记录区 `0x1250 + bank × 64`；每记录 **64 B = 12 组 (Cb,Cr) int16（48 B）+ 8 个 int16 尾（16 B）**。
- 尾部 16 B 不是纯填充：记录 16 的尾是全场唯一非零 `f6 ff f3 ff 95 ff 31 00`。整条覆盖会把尾一并清零，曾把 FL 变成黑白。
- 尾部 10 字节 `[16,8,14,10,12,9,15,11,13,19]`（在 `0x1238` 结束前）是「出厂 profile 号」，**不是**外观→记录表（ST 记录实测为 0，对不上）。
- 空记录（全零）：**22–27、30、31**。有数据：0–21 的大部分、28、29（早期只枚举 32 槽是低估，`CHROMA_SPAN = 64*54`）。

实测「外观 → 色度记录」：

| 外观 | 记录 | 依据 |
|---|---|---|
| ST | 0 | 涂色实验 |
| VV | 1 | 涂色实验 |
| NT | 4 | 涂色实验 |
| PT | 6 | 涂色实验 |
| FL | 8 | FL 与别名 1FL/2FL 同步变黑白 |
| SE | 9 | 涂色实验 |
| IN | 10 | IN 与 3IN 同步变荧光绿 |
| SH | 11 | SH 与 4SH 同步（整体偏粉） |
| VV2 | 14 | 涂色实验；5VV2 同步 |
| BW | 未知 | 黑白看不出来 |

**记录的 (Cb,Cr) 是反向作用**：存 `(0,+300)` → 画面偏绿；存 `(+300,+300)` → 荧光绿；存 `(-300,-300)` → 整体偏粉。判读一律按「画面 ≈ −存值」。

### 4.2 CP 色度参数表的两个旋钮

- `+55` → mode 19 的记录号；`+56` → mode 20 的记录号。**这条来自 FireHydrant 文档，我们没能独立复现**：唯一一次「5VV2 变绿」事后归因于 VV2 自己的记录 14 被涂色（E13 三次配对证明 5VV2 ≡ VV2）。当前状态：**未证实**，见 §13 第 5 条。
- **`+51..+54` 无效**：曾写 `[2,3,5,7]` 且把记录 2/3/5/7 涂成纯色，画面无任何变化。
- **`+57..+60` 会让相机切 ST 时闪屏重启**（写过 `[22,24,26,27]`）。这是 CP 侧只给两个额外模式留位置的硬边界。
- 一条更靠得住的边界：**A 层只在 `w1 == 0`（基底外观 = ST）时接管**，所以六个自定义槽里只有基底是 ST 的那一个能吃到 mode 19/20 的映射；`5VV2`（基底 VV2）永远走原厂路径。

### 4.3 CP 矩阵单元 `0x02A4000D`（28,672 B）

参数表 `0x196..0x1e0`，矩阵 `0x1e0 + slot × 768`，每槽 768 B。参数 `+55/+56` 写成 6/4 看不出变化（已还原为 0）。

### 4.4 会话（真正稀缺的资源）

`cp.session()` = `patches.install()` → `_cooldown`（`SESSION_GAP` 默认 50 s）→ `device_lock` → `run_authentication(None, 0x0336, …)` → 开头 `_clear_temp` 删 `/tmp/jiritsu/tmmc.jit` 与 `tmmc.dat` → yield `CpChannel` → finally `STOP_SENSER`。

实测：**一个会话里连续 36 次 execute（2 stat + 34 read）不会掉线**；「8~13 次往返就掉」的旧笔记只适用于 CP 单元 + 145 KB 文件混写。

`cp.read_unit` / `cp.write_unit` **不是模块函数**，是 `CpChannel` 的方法：

```python
with cp.session(progress=print) as ch:
    raw = ch.read_unit(cp.CHROMA_UNIT)
    ch.write_unit(cp.CHROMA_UNIT, data)
```

### 4.5 持久化

CP 是 RAM，正常关机时才写进 `/setting/BACKUP.BIN`（色度 `0x1B2140` 8,192 B、矩阵 `0x1B6870` 28,672 B），**关机等满 1 分钟再开机才落盘**，立刻开机会丢。

1. **5VV2 与 VV2 在三次配对中逐像素几乎相同** → 5VV2 是纯别名，任何「5VV2 变了」都是因为改了 VV2 自己的记录 14。
2. **FL 偏粉 = 蓝通道比其它外观高 8–10%，亮度也高约 25%**（Y 145 vs 117，B/G 0.97 vs 0.89）。
3. ST 与 PT 亮度几乎相同（117.6 / 117.1）。

### 6.2 配方（`docs/looks-profile.json`，四条的 record_hex 原样可写）

| 外观 | 目标 bank | 配方 | 离线 RMS | 矫正率 |
|---|---|---|---|---|

| NC | NT（4） | 全 1.00、pair2 × 0.62 | 0.173 | 82.7% |

另有更优但**没进仓库**的 CC 配方：`pair2 × 0.60 + pair6 = 0`，离线 RMS 0.164（见 `docs/LOOK-COLOR.md`）。

## 8. 事故与恢复方案

### 8.1 事故

`.data/tmp/ramp_zero.py --zero` 把 `/cp/cpapp-b.bin` 的 `0x10D02B8` 3,872 B 写成全零，回读一致，随后相机黑屏无限重启。备份存在（见 7.2）。

实测 USB 行为：只剩 `VID_054C&PID_0D68`（`USB\VID_054C&PID_0D68\5&274D72C6&0&1`，service `HidUsb`，「USB 输入设备」），每 3 秒出现 1.5 秒。拔 SD 卡、换电池、放静电都无效。

### 8.2 扇区定位（已离线算好）

`/cp` = FAT12：512 B/扇区、32 扇区/簇（16 KiB）、reserved 32、2 个 FAT、FAT 32 扇区、root 512 项、总 48,844 扇区；root 在 `0xC000`、数据区在 `0x10000`。`CPAPP-B.BIN` 首簇 145、**1,093 簇全连续**、首扇区 4,704（`0x1260`）。

```
文件偏移 0x10D02B8
  → 簇索引 1076 → 簇 1221
  → 绝对扇区 39,137（= 128 + 1219×32 + 1）
  → 簇内字节偏移 184
需要覆盖 3,872 B → 从扇区 39,137 起写 9 个扇区：39,137 … 39,145（4,608 B）
  （8 个扇区只到 0x10D1200，会把模式表尾部 128 B 漏在外面，所以取 9 个）
顺带覆盖 0x10D11D8 起的 168 B 模式表 → 一并写回 FL23 原值
```

离线自检（已跑通）：按 `0x10000 + (145-2+i)*0x4000` 从 `firmware/nflasha8-2.00.bin` 拼 1,093 个簇再截到 17,892,024 B，与 `firmware/cp/cpapp-b.bin` **逐字节相同（0 差异）**——证明簇链连续、扇区换算无误。

一个坑：**分区镜像里的「文件偏移」不是「分区偏移」**。我一开始直接把 `part[0x10D02B8:…]` 当那段来校验，看到 3,589 个非零字节，差点误判「出厂这段不是零」；必须按簇算出 `39,137*512+184` 再读，那里才是真正的全零。

### 8.3 恢复路线：RP2040 Pico 冷启动注入

来自用户自己的项目 `refs/a6700-powerful/硬件说明.md`：Pico 用 **GP28 —470Ω— USB-C 测试板 D−** 打开漏波形，让相机进入冷启动接收，把程序注入 RAM `0xFE020000`，由该程序提供 USB Fastboot。**不需要相机能启动到应用层。**

采购清单：400 孔面包板、杜邦线、RP2040 Pico（须引出 VBUS 物理 40 脚 / GP28 / GND）、USB-C 24P 测试板（公头）、470Ω ×1、56kΩ ×2（分别串 CC1/A5、CC2/B5）。5V 只从 Pico VBUS 取，**不接 VSYS/3V3**。

上游现成的 `已验证文件/相机只读引导.bin` **不给写**（构建脚本断言 `mmc_write_blocks`/`cmd_flash`/`cmd_download` 等符号不得链接）。所以要自己造可写版：

- 源码：`refs/ILCE-7M4-RE`（commit `2328d18ce640e6c8cd9341efcf0043ce9042a135`）的 `payloads/fastboot`，其 `fastboot.c` 本身带 `flash:` / `download:` / 稀疏镜像写入 / `mmc_write_blocks`。
- A6700 专用部分（`main.c` 的 `write32(0xF102E034, 1u<<16)` 等、`no_cp.c` 打桩、`usb.c` 诊断）用 `refs/a6700-powerful/源码/脚本/构建相机引导.py` 生成的版本 —— 用桩 `--cc/--ld/--objcopy/--nm` 跑它，就能把 `生成源码/{main.c,fastboot.c,no_cp.c,usb.c}` 吐出来，再配**未修补的上游 fastboot.c** 重编译。
- 工具链：`.venv/Lib/site-packages/ziglang/zig.exe`（zig 0.13.0，`aarch64-freestanding` + lld）。
- 目标尺寸约束：payload ≤ `0x10000`，`load_entry 0xfe020000`。

写入方式（一次稀疏写，9 个块 / 4,608 B）：`download:` 推一个 Android sparse 镜像（`blk_sz=512`、SKIP 39,137 + RAW 9、`total_blks=39,146`），然后 `flash:nflasha8`。`resolve_part()` 只认 `nflashaN` 的十进制槽号，`nflasha8` 就是 `/cp`。现成镜像见 §7.2，生成器 `tools/fl23_recovery.py`。

注入流程（`refs/a6700-powerful/操作手册.md`）：相机 OFF + 取电池 ≥5 s + 测试板先不插 → Pico 连电脑、烧 `Pico-v2.uf2`、`--检查Pico`（预期 `a6700_pio_od 2`）→ `--载荷 … --开始注入` 看到 `ARMED` 再插测试板、装电池、拨 ON → 45 条记录发完 → **先拔整个测试板**，再把数据线从 Pico 移到相机 → `查询Fastboot.py --分区表`。

### 8.4 风险

- 只写 9 个扇区，不碰分区表、不碰 loader、不碰引导区；但**写错内容会二次砖化**，所以内容必须先用 `.data/writes/ramp-before-*.bin` 校验 sha256 再发。
- 可写 payload 是我们自己编的，`cmd_flash` 路径没在实机验证过；先用 `oem partition dump nflasha8 <off> <len>` 只读回读确认通道通，再写。
- 彻底失败时的兜底：卡根目录有官方 `BODYDATA.DAT`（1,024,017,848 B），但**相机起不来就刷不了卡升级**，所以这条路依赖 Pico 至少能进 Fastboot。

### 8.5 到货即执行：恢复操作手册

素材全部离线备好（§7.2）。**任何一步结果不符就停手**，不要连着往下做。

| 镜像 | 大小 | 覆盖 | 用途 |
|---|---|---|---|
| `restore-b.sparse` | 12,556 B | 24 个扇区、10 段（`4960`、`7181`、`7183`、`7314`、`7322`、`11036-11038`、`11042-11043`、`17429-17432`、`24566`、`39137-39145`） | **首选**：B 层 33 窗全部回出厂 |
| `ramp.sparse` | 4,660 B | 扇区 39,137–39,145（9 块） | 最小改动：只把曲线区与模式表写回 FL23 值 |

两者都是 Android sparse（`blk_sz=512`、RAW chunk），重建命令 `tools/fl23_recovery.py ramp|restore-b`。

**第 1 步 · 注入 payload 起 Fastboot**：按 §8.3 接线（Pico `GP28` —470Ω— 测试板 `D−`，`CC1`/`CC2` 各串 56kΩ），刷 `已验证文件/Pico-v2.uf2`，跑 `进入Fastboot.py`，看到 `ARMED` 后插测试板、装电池、拨 ON。`查询Fastboot.py --分区表` 能列出 `nflasha8` 即成功。

**第 2 步 · 只读确认目标扇区（关键）**

```
fastboot oem partition dump nflasha8 98E1 9
```

`0x98E1 = 39,137`，offset/size 都是**十六进制扇区号**。回读 4,608 B 的**前 184 字节应等于出厂数据**（与 `.data/recovery/ramp.img` 前 184 字节逐字节相同），其后 3,872 B 应全是 `00`（因为曲线区被写零了）。对不上就停手——说明簇映射或分区名错了。

**第 3 步 · 写入**

```
fastboot download .data/recovery/restore-b.sparse
fastboot flash nflasha8
```

`download:` 首 4 字节是 sparse magic，payload 会自动走 `flash_sparse`，按块号 `mmc_write_blocks` 写入（`nflasha8` 不加密，不走 XTS）。

**第 4 步 · 回读再断电**：再 `oem partition dump nflasha8 98E1 9`，此时应等于 `ramp.img`（FL23 曲线区）。然后相机 OFF → **先拔整个测试板** → 取电池 ≥5 s → 只装电池开机。

**失败分支**

- 回读内容对不上 → 不要 flash，回头核簇表（root 目录项 `CPAPP-B.BIN` 首簇 145、1,093 簇连续）。
- `flash` 报 sparse 头错 / 越界 → 换 `ramp.sparse`（只有 2 个 chunk，最小面）。
- 写完仍黑屏 → 说明还有我们没写过的区被破坏，此时只剩官方 `BODYDATA.DAT`（卡根目录，1,024,017,848 B）恢复。

## 10. 教训清单

1. **参数越界会崩机**：CP 参数表只有 `+55`/`+56` 两个额外模式位，写 `+57..+60` 让相机切 ST 就重启。
2. **真正致命的不是「写坏代码」而是「写坏数据区」**：33 窗补丁删掉最多是没效果，写零 3,872 B 曲线区直接让相机起不来。数据区的每次写入都该先做「能不能冷启动」的风险评估。
3. **别名机制会骗人**：任何「某个自定义槽变了」都要先确认它的基底外观自己的记录是否变了。5VV2 三次「变化」全部是 VV2 的变化。
4. **A 层的门是 `w1`（基底），不是 `w0`（菜单序号）**。搞错这一层，后面所有 C 层实验都喂给死支路。
5. **整条覆盖记录会连带清零尾部 16 B**，那里面有单色/饱和度之类的标志位。要么按字节 diff 写，要么先读后改。
6. **写之前先留原始字节**：`.data/writes/*-before-*.bin` 这类快照是唯一能把相机救回来的东西。曲线区就是有 `ramp-before-20261026T035953.bin` 才有得救，否则连「原始内容」都要靠猜。
7. **先离线演练再真机**：`firehydrant_drill.py` 那一轮 33/33 窗核对，避免了真机写坏的可能。

## 11. 恢复之后该做什么

按优先级：

1. **抢回可启动状态**：用 `restore-b.sparse`（首选，§8.5）或 `ramp.sparse` 写回扇区 39,137–39,145（4,608 B）。开机确认能启动、菜单仍 16 项。
2. **决定 B 层去留**：如果偏粉要彻底排除，`tools/fl23_write.py restore-b` 把 33 窗全部回出厂，菜单回到 14 项；确认 FL 是否仍偏粉，得到干净结论。
3. **回到真正的目标**：内置 10 项回出厂 + 四条配方写回内置记录（CC→记录 6、NC→记录 4、PF→记录 1、NF→记录 14）。这条路线**已被真机证明可用**，是唯一确定能交付的形态。
4. **「独立槽装 CC/NC」已证伪**：需要 cpapp 侧的 mode→记录映射扩展 + FireHydrant 那 911 B 本体，而字节没有公开。除非逆出 C 层，否则不要再投入。
5. **FL 偏粉未结案**：模式表已排除；剩下 A 层 112 B 与曲线区两个变量，恢复后再用同一场景拍 ST/PT/FL 三张做对照。

## 13. 存疑与未验证清单

1. **「mode 19/20 在静拍路径数据不成立」仍是假设**：唯一证据是「slot1 强指 mode 19 后选 ST 闪屏重启」，也可能不是数据不足，而是那张表下标越界。
2. **FL 偏粉未定案**：模式表已排除（归零后照样粉，WHM00173 `B/G` 0.982，Y 146.5），曲线区没验证——验证它的那次写入就是炸机动作。
3. **6BW 黑白**：色度层怎么写都无效，判断单色来自基底 BW，未验证。
4. **BW 的色度记录号未知**（候选 2/3/5/7/12/13/15..19）。
5. **`+55` 是否真决定 mode 19 的色度记录**：FireHydrant 文档写「参数 55 → 色度槽 23」，但我们唯一一次「5VV2 变绿」事后归因于 VV2 自己的记录 14 被涂色，`+55` 没有被独立确证过。
6. **矩阵单元是否有一套并行的 mode→slot 参数**：只试过 `+55/+56` 两个字节。
7. **记录尾 16 B 的语义未知**：涂记录 8 让 FL 变黑白，说明那 16 B 不是填充。
8. **六个自定义槽的基底没有逐一对过**：目前只有 `5VV2`（基底 VV2）、`1FL`（基底 FL）、`6BW`（基底 BW）三条实证。
9. **恢复之后 A/B 层保留到什么程度，要用户先定**：`restore-b` = 回出厂（菜单 14 项）；`ramp` = 回 FL23 可用态（菜单 16 项，但静拍下那两项不成立）。
