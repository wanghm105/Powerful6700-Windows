# 自定义外观（Classic Chrome / Classic Negative / 理光正片负片）

适用：Sony A6700（ILCE-6700）+ 固件 **2.00**，Windows 端工具 Powerful6700。
本文是最终状态说明；调查过程、失败路径与全部实测数据在 [LOOK-COLOR.md](LOOK-COLOR.md)。

## 0. 图形界面入口

程序左侧导航有「自定义外观」页，页里两张卡片：

- **颜色**（当前状态）：点「检测当前状态」读取四条色度记录（只读，同时也会读菜单文字），点「写入配方」写入并回读校验，点「还原本页外观」写回出厂值。写入后界面会显示每条记录处于「已写入配方 / 出厂外观 / 已被其它改动」中的哪一种，并单独报告与本页无关的记录是否被改动。
- **菜单文字**：点「写入菜单文字」把 PT/NT/VV/VV2 的显示名改成 富士CC / 富士NC / 理光PF / 理光NF；点「还原菜单文字」按基线整份还原；点「导入基线…」可以手动指定一份出厂语言资源。细节见 7.1。

命令行等价：

```powershell
python tools/looks_apply.py --confirm yes-write   # 相机切到 USB 存储模式
```

## 2. 原理（三行）

- 外观颜色存在 CP 单元 `0x02A40001` 的色度表里：`0x1250 + bank*64`，每条 64 B = **12 组 (Cb,Cr)**（24 个 int16）。
- 菜单里的每个外观按固定 bank 读色度（ST=0、VV=1、NT=4、PT=6、FL=8、SE=9、VV2=**14**）。
- 12 组里只有 **第 2 组（pair2）** 是有用的宽把手：压它 ≈ 把 60–180° 的暖区整体下压（宽约 90°），其余 11 组叠不出局部形状。

名称走 `/usr/share/app/string_simplifiedchinese_f.uxc`（UXC 资源，改记录文本 + 重排索引表），断电保留。

## 3. 一键写入

```powershell
# 相机切到「USB 存储 / MSC」，先干跑确认计划
python tools/looks_apply.py --dry-run
# 真正写入（整单元读基线 → 写 → 回读校验）
python tools/looks_apply.py --confirm yes-write
```

配方在 [looks-profile.json](looks-profile.json)，改配方改这个 JSON 即可；
单条也可用 `tools/look_write.py --look "CC=6:6:1.00@2*0.52"` 直接写。

改名（一次性，写前自动备份到 `firmware/uxc/`）：

```powershell
python tools/uxc_grow.py --set 0x021c6654/0x021c6f8b="Classic Chrome" `
    --set 0x021c6434/0x021c7002="Classic Negative" `
    --set 0x021c687b="Positive Film" --set 0x021c689a="Negative Film" --confirm yes-write
```

## 4. 验收方法（可复现）

```powershell
# 同一场景、同一机位，先拍 ST，再依次拍四个外观，各带 .ARW
python .data/hue_eval.py <ST.jpg> <LOOK.jpg>     # 输出 12 档比值、最优整体缩放 s、RMS
```

注意事项（踩过的坑）：
- **MSC 模式下不能拍照**，拍完必须切回拍照模式，写之前再切回 MSC。
- 每轮场景/光线不同，**跨轮的绝对比值不可比**，只能比同一轮里的「外观 vs ST」。
- 判读顺序时先确认文件顺序（第一张必须是 ST），否则 RMS 会算反。

## 5. 边界（明确做不到的）

| 想要 | 现实 |
| --- | --- |
| 富士的 S 形影调 | **色度层做不到；影调层在 cpapp 模式表 + CP 槽参数里**（2026-10-25 修订）。那 9 条 1024 B 恒等斜坡（`0xfe0b50` 起）确实是死数据，但 FL2/FL3 的观感由「42 项 CP 候选模式表 + 每槽 8 项参数」表达，不经 gamma 斜坡；我们的拟合目前只用了色度一层。见 `AI-HANDOFF.md` §18。 |
| NC 的窄带品红缺口（0.34） | **只能近似**。目标形状靠 pair2 的宽下压逼近到 RMS 0.173；真正的窄带需要逐色相权威，而 `0x02A4000D` 做不到（见下）；矩阵层（每槽前 576 B）尚未标定，是下一轮的自由度。 |
| 理光正片的「压红抬黄绿」、负片的「压红压蓝但抬正蓝」 | **做不到**，停在低饱和轻量版。 |
| `.cube` 直接导入 | **做不到**。相机只吃自己的色度表；A7C2 的 `.a7look`（缺 curve/matrix/chroma 三层）与 `.dcp`（Adobe PCS 线性 RGB 的 HSV 空间）都无法搬到 12 组 (Cb,Cr) 模型。 |

## 6. `0x02A4000D` 的 16 个块（已探明，但不是解法）

- 单块整填 +20000 可定位归属：**block2 = VV 主表**、**block3 = NT(NC) 主表**、**block4 = 仅 PT 的蓝端**。
- 填 1–8 时 PT/NT/VV/FL/IN 五个一起爆；VV2/SH/SE 从不响应，它们的表在 9–15。
- 但**基线量级的修改测不出来**：整块 × 0.6 后平均色度 0.0620（基线 0.0621）；只有灌 +20000 这类超载才显形，
  且响应与"填了几个值"近似线性（16/8/4 个值 → 蓝 7.67/4.58/2.98×）。
- 结论：它是**细调增量表**，不是颜色曲线的权威，做不出逐色相性格。数值饱和，也不能用幅度排序区分归属。

## 7. 还原到出厂

1. `python tools/cp_verify_factory.py` —— 逐单元与 `/setting/def/BACKUP.BIN` 的出厂副本比对；
2. `python tools/restore_units.py` —— 把出厂值写回 CP RAM；
3. **正常关机、等满 1 分钟再开机** —— 相机才会把 RAM 覆盖进 `/setting/BACKUP.BIN`（少了这步会出现"当场对、重启又变"；关机后立刻开机同样会丢，实测见 `docs/CC-CN-PLAYBOOK.md` 第 6 节）；
4. 名称还原：见下面「7.1 菜单文字」——GUI 里点「还原菜单文字」即可；等价的手工路径是把 `firmware/uxc/string_simplifiedchinese_f.uxc.20261023T233448Z.bin`（145,612 B，sha256 fe263360c15b5530）整份写回 `/usr/share/app/string_simplifiedchinese_f.uxc`，写完 `flash.truncate` 到 145,612 B，再整份回读比对。

### 7.1 菜单文字（名字）

颜色记录在 RAM 里（关机才落盘），菜单文字在 `/usr/share/app/string_simplifiedchinese_f.uxc` 这个 ext2 文件里（一写就持久）。所以两件事分开写、分开还原，界面上也是两张卡片。

- **记录定位**：每个外观有两条记录（菜单短名 + 列表名），出厂文字就是槽位缩写本身。ST=0x021C658E；PT=0x021C6654/0x021C6F8B；NT=0x021C6434/0x021C7002；VV=0x021C687B/0x021C6F80；VV2=0x021C689A/0x021C6F4D；FL=0x021C6CC9；IN=0x021C6857；SH=0x021C6961；BW=0x021C65F8；SE=0x021C658A。`menu_slot` / `menu_text` 写在 `docs/looks-profile.json`。
- **写入**：短名（2 字节）装不下「富士CC」（7 字节），所以走 `uxc.rename_all` 的整块后移 + 索引表重写；写回按 `flash.WRITE_BLOCK`（128 KB）分块，文件变短时 `flash.truncate`，每块由相机侧载荷 pwrite + fsync 后回读比对（不一致返回状态 9），主机侧最后只复核长度。四个外观改完从 145,612 → 145,676 字节（实测算术值，+64）。
- **还原三档**（界面 `baseline` 一行会说明当前是哪一档）：
  1. **整份基线**：写入前自动把整份资源存进 `.data/looknames/`（`index.json` 记 sha256/字节数/来源/时间），还原时整份逐字节写回并校验基线自身哈希。这是「无损」那一档。
  2. **短名回写**：本地没有基线时，只能把文字改回出厂短名（PT/NT/VV/VV2）。实测这份资源「改名 → 改回短名」后与原文件**逐字节一致**（长度也回到 145,612），但这只是实测行为，不能当承诺：别的固件版本或别的改动顺序不一定成立。
  3. **不写**：没有差异就只报告。
- **导入基线**：手上有出厂 `*.uxc` 备份时，界面「导入基线…」会校验 magic/`kind=8`/外观记录是否齐全，再收进基线库。
- 纯逻辑测试在 `tests/test_looknames.py`（合成资源，不碰相机）。

## 10. 2026-10-26 订正：别名、记录布局与失败的「独立槽」路线

> 本节是 `docs/FL23-FULL-RECORD.md` 的摘要。§1–§9 的配方与 RMS 数字仍然有效，只有下面几处要按这里读。

- **bank 映射补两个**：IN = 10、SH = 11（原有 ST 0、VV 1、NT 4、PT 6、FL 8、SE 9、VV2 14 不变）；BW 没有独立色度记录。
- **记录布局订正**：64 B = 12 组 (Cb,Cr) int16（48 B）+ 8 个 int16 尾巴（16 B）。「其余全零」只对出厂态成立；尾巴带语义，整条覆盖会翻掉「单色/饱和度」类标志位（涂记录 8 → FL 变黑白）。
- **配方符号**：记录里存的是反向偏移——存 `(0,+300)` 画面偏绿、存 `(+300,+300)` 荧光绿、存 `(-300,-300)` 整体粉。判读一律按「画面 ≈ -存值」。
- **六个自定义槽是别名，不是新外观**：`1ST / 2FL / 3IN / 4SH / 5VV2 / 6BW` = 序号 + 基底名，逐像素等于基底（`5VV2` vs `VV2` 三组配对 ΔY 0.2–0.4%）。给别名换色 = 给基底换色，两者一起变。
- **「把配方搬进独立槽」已证伪（2026-10-26）**：A 层 override 只在基底 = ST 时触发；FireHydrant 文档里的 `+55 → 槽 23` / `+56 → 槽 25` 没能独立复现（涂 `(400,400)` 极端值也不进画面）；`+51..+54` 无效，`+57..+60` 会让 ST 闪屏重启。
- **四条配方的落点仍然只有内建记录**：CC → PT（记录 6）、NC → NT（记录 4）、PF → VV（记录 1）、NF → VV2（记录 14）。想要「内置保持原厂 + 额外两套」，目前无路。
